# Spec 039: Per-run proposal patches

## Status

**(Implemented)**
Proposal patches become their own business object on disk (not a trail comb artifact): AFK and HITL proposal finalization archive the diff bytes produced by the existing collector, and synthesized `MUTATION` points at the file instead of inlining the diff. This is a history of proposals, with explicit capture and publication limitations, not proof of the state a Guard approved or a repository backup. Supersedes the 64 KiB object-store offload. Replaces the backlog item "A reviewed diff does not outlive the review". Preview/export budgets and any future retention inside an active Standing Trail remain open decisions in Further Notes.

Shipped with the `internal/patches` store, the shared `internal/proposal` finalizer, the `patches` export slice, and the Console proposal-patches endpoint. Canonical behaviour: [architecture overview](../architecture/overview.md) § Run tree layout, [event contracts](../reference/event-contracts.md) § `MUTATION` refs, [interactive sessions](../guide/interactive-sessions.md) § Proposal finalization, [CLI](../guide/cli.md) (`--include patches`, retention). The budget values in Further Notes are implemented as proposed: 512 KiB per Console preview, 512 KiB per inlined export body, and 8 MiB of raw inlined patch-body bytes per export.

## Problem Statement

Once a Flight Trail is merged, the proposal diff associated with an individual run is hard to recover for retrospective analysis of Bee behavior.

- The review worktree is removed at merge, while git history does not preserve the association between each proposal attempt and its captured diff.
- `MUTATION/code.proposal.*` inlines the diff in the payload up to 64 KiB and above that stores an object in the JetStream object store, replacing `diff` with a `ref`. Nothing reads that object: no fetch command, no Console surface, no export slice. On a real trail the export says "No trail artifacts in the comb" and an 18-file, +1433/−14 reviewed change is gone.
- Event payloads are not a durable archive for Beekeepers either: `paseka replay` prints kinds and agent ids without payloads, and both export and the Console Timeline read the per-run event log, which never receives runtime-synthesized mutations. Purging the bus removes the last copy.
- Meanwhile the inline diff is noise for the review itself. Guard reviews the working tree with git commands — the prompt says so explicitly — so the pasted diff is ignored. It costs JetStream payload size and prompt tokens, and above the threshold it silently becomes an unreadable reference, making the behavior size-dependent for no gain.
- Recomputing a diff later cannot recover the output collected when the run finished. The existing collector uses the captured workspace baseline to select changed files, then diffs those files against the current `HEAD`. This is useful context for behavioral analysis, but it is neither a strict delta from the run's starting dirty state nor a complete workspace snapshot. Storing its output preserves that context without strengthening those guarantees.

## Solution

Introduce the **proposal patch**: a new, first-class record — one immutable diff file per runtime-generated proposal attempt from a successfully completed AFK run or HITL session, plus a small metadata sidecar. The sidecar distinguishes confirmed publication from an unpublished or unconfirmed attempt. It is deliberately *not* a trail comb artifact:

- Comb artifacts are things a Bee hands off that live only in the trail and are not part of the repository code (notes, specs, checkpoints, journals). A patch is a snapshot of code changes. Keeping them in one bucket would make `artifact.written` announcements, artifact kinds, comb baselines, and Trail Comb listings lie about what the trail contains.
- Patches live on disk under the trail's run tree, next to the run directories but in their own reserved subdirectory. They survive worktree removal at merge, and are cleaned by the retention commands that already remove run data — no new cleanup path, no bus-side lifecycle.

The synthesized `MUTATION` payload carries a colony-root-relative `ref` to the patch and no inline diff. The patch reader resolves it against `ColonyRoot`, independently of the consumer's cwd, worktree, or sector. Comb readers keep their existing containment rules and cannot resolve patch refs.

Guard continues reviewing the repository in its assigned workspace. For new runtime-generated proposals, neither patch bytes nor an archive pointer are copied into the Guard's task or prompt. The event ref serves the human history surfaces. Saving a proposal does not assert that the Guard reviewed or approved those exact bytes, and does not correlate a verification with an immutable repository state.

Beekeepers get two new read surfaces over the patch store: a `patches` include slice in `paseka export`, and a dedicated Queen Console view per trail that sits beside the live merge gate rather than replacing it.

The archive preserves whatever bytes the existing collector successfully returns. It does not guarantee exclusion of earlier edits within a file the run changes, capture of untracked files or changes committed during the run, binary contents, or successful capture of deletions and renames. `baseSha` records baseline context; it is not a promise that applying the patch to that commit reconstructs the workspace. Patch application, binary restoration, and exact reconstruction of a run or review state are explicitly unsupported guarantees. Improving the collector is outside this spec.

## User Stories

1. As a Beekeeper, I want the diff captured for a proposal attempt to remain readable after the trail is merged, so that I can analyze the Bee's behavior weeks later without treating it as proof of what a Guard approved.
2. As a Beekeeper, I want `paseka export --include patches` to list every complete proposal record and inline bodies within the export budgets, so that an offline report explains both captured proposals and omitted content.
3. As a Beekeeper, I want `paseka export` to keep working with no NATS server reachable, so that audit never depends on bus availability.
4. As a Beekeeper, I want the patch store to be cleaned by `paseka purge --runs` and `paseka prune --runs`, so that retention is one mechanism instead of two.
5. As a Beekeeper, I want the patch to survive a `paseka purge --bus` of that trail, so that removing bus state does not silently destroy the code record.
6. As a Beekeeper, I want the Trail Comb listing and `artifact.written` announcements to stay free of patches, so that "what this trail handed off" keeps meaning handoffs.
7. As a Beekeeper, I want the guard prompt to stay focused on the working tree, so that review quality does not depend on how big the patch is.
8. As a Beekeeper, I want archive bytes and archive pointers to stay out of the Guard task for new runtime-generated proposals, so that the Guard reviews its assigned repository workspace.
9. As a Beekeeper, I want one patch per runtime-generated proposal attempt, labeled with its publication state, so that a rework cycle leaves a readable history of the attempts.
10. As a Beekeeper, I want a rework cycle's second attempt to not overwrite the first attempt's patch, so that the rejected attempt remains inspectable.
11. As a Beekeeper, I want no patch file when the collector returns an empty diff, so that the patch list has no empty entries without implying that the workspace was unchanged.
12. As a Beekeeper, I want no patch file for a run whose Bee does not auto-publish a proposal, so that non-mutating Bees (Scout, Archivist) leave no proposal records.
13. As a Beekeeper, I want the archive to preserve the existing collector's output and document its attribution limits, so that a patch containing earlier edits is not mistaken for a strict delta of one run.
14. As a Beekeeper, I want root-workspace proposals recorded the same way as isolated ones, so that both proposal kinds are auditable.
15. As a Beekeeper, I want a very large patch stored whole rather than dropped, so that size never decides whether the record survives.
16. As a Beekeeper, I want a patch too large to inline into an export to be listed with its size and a clear reason instead of silently missing, so that its absence is diagnosable.
17. As a Beekeeper, I want each patch entry in an export to carry run identity, Bee, AFK/HITL mode, task, proposal kind, workspace, baseline context, summary, size, time, and publication state, so that the archive explains each patch without the event stream.
18. As a Beekeeper, I want that metadata to come from a sidecar written next to the patch, so that a purged bus does not leave orphan patch files with no context.
19. As a Beekeeper, I want the Console to show a trail's proposal patches as a list, so that I can pick which one to inspect.
20. As a Beekeeper, I want the Console patch list to be separate from the live merge gate preview, so that "what each run proposed" and "what is staged now" are not confused.
21. As a Beekeeper, I want the Console patch view to show file count and size per patch, so that I know what I am about to open.
22. As a Beekeeper, I want the Console to handle a patch larger than a phone screen, so that a huge patch does not break the page.
23. As a Beekeeper reviewing a trail, I want the event timeline to stay compact, so that one mutation event is not a wall of diff text.
24. As a Beekeeper inspecting the JetStream stream directly, I want the mutation payload to be small and uniform, so that consumers do not branch on diff size.
25. As a Beekeeper, I want no JetStream object store dependency for proposal review, so that a missing object store cannot break the record.
26. As a Beekeeper with historical trails that have inline diffs, I want those trails to keep exporting as they do today, so that this change is not a migration project.
27. As a Beekeeper, I want a trail with no patch directory to read as an empty patch list rather than an error, so that old and empty trails behave like absence, not failure.
28. As a Beekeeper, I want `paseka purge --bus` to still delete legacy diff objects, so that historical object-store bytes do not leak after this ships.
29. As a Beekeeper running swarm mode, I want one patch per variant run, so that best-of-N attempts are individually inspectable.
30. As a Beekeeper, I want the patch file name to identify the run, so that a patch found on disk is traceable to its run record.
31. As a Beekeeper, I want the patch ref in the payload to resolve relative to `ColonyRoot`, so that a reader does not confuse a sector or isolated worktree with the archive root.
32. As a Beekeeper, I want a hand-authored `MUTATION` with an inline diff to remain valid, so that a colony script publishing its own proposal is not broken by this change.
33. As a Beekeeper, I want a run or session whose execution failed or was aborted to leave no synthesized proposal record, so that partial execution is not presented as a completed proposal attempt.
34. As a colony author, I want the runtime to own patch writing, so that patch layout and metadata are not something each Bee reimplements.
35. As a colony author, I want the patch directory to be reserved and never treated as a Bee run directory, so that projections, timelines, and run listings stay correct.
36. As a colony author, I want the patch directory to not be injected into prompts as a writable handoff location, so that the comb contract ("write here for handoff") stays unambiguous.
37. As a colony author, I want new synthesized proposal refs to identify archive paths while legacy object-store refs remain recognizable, so that a change of storage does not reinterpret historical references.
38. As a colony author, I want proposal validation to keep accepting a payload with only a `ref` and summary, so that dropping the inline diff stays a runtime change, not a contract break.
39. As a Beekeeper, I want review guidance to direct the Guard to its repository workspace, so that the archived proposal is not substituted for the code being reviewed.
40. As an operator, I want run retention to describe its scope honestly, so that I know an active Standing Trail can retain an unbounded proposal history until it is explicitly cleaned.
41. As an operator, I want `paseka prune --bus` and `paseka prune --runs` to stay independent for patch purposes, so that choosing a filesystem-only cleanup does not need a bus server.
42. As a Beekeeper, I want the patch store to be gitignored, so that proposed code never reaches a commit by accident.
43. As a Beekeeper, I want captured diff bytes preserved without lossy UTF-8 conversion and previewed only when suitable for text rendering, so that a history record is not silently rewritten to fit a UI.

45. As a Beekeeper, I want a resumed provider session to create a new run-scoped record with a fresh baseline, so that resuming does not overwrite an earlier proposal.
46. As a Beekeeper, I want incomplete file writes to stay out of ordinary patch listings and be diagnosable, so that a crash does not expose a half-written record as valid history.
47. As a Beekeeper, I want publication errors and uncertain broker outcomes to be visible beside a retained patch, so that a saved attempt is not mistaken for a confirmed bus event.
48. As a colony author, I want a retry of the same proposal to reuse its immutable bytes and original event, so that retries cannot silently replace the history of a run.
49. As a Beekeeper, I want a patch-storage error to prevent publication of a broken ref and be visible in the run or session outcome, so that archiving failures are actionable.
50. As a Beekeeper, I want an explicitly emitted proposal to keep its existing contract without triggering a duplicate synthesized proposal, so that adding HITL finalization does not dispatch a Guard twice for one proposal.

## Implementation Decisions

1. **New store, own reserved subdirectory.** Patches live at `.paseka/runs/<traceId>/proposals/`. The trail comb remains `.paseka/runs/<traceId>/artifacts/` and keeps its existing meaning. The new subdirectory is registered in the runs package's reserved-subdirectory set *and* its no-per-agent-events set, so it is never treated as a Bee run directory and never merged into timeline event reads. Both registrations are a decision, not a listing detail: the reserved set keeps run projections from reading it as a Bee, and the skip set keeps it out of trail event merges even though the sidecar retains an event envelope. The `console` directory is the contrasting case — reserved, but not skipped, because it is a real run directory that happens to hold human-producer audit events.
2. **Own package with its own reader.** A new `patches` package owns root resolution, write, list, metadata read, and content read. Refs resolve against the owning `ColonyRoot`, never against a Guard cwd, a sector, or a worktree root. Reads and writes enforce containment within that trace's proposal store, including symlink escapes. It does not reuse comb write helpers: comb resolution intentionally rejects any path outside the comb, and patch paths must not become addressable as comb refs.
3. **One file plus a sidecar per run.** `<agentId>.patch` holds immutable diff bytes; `<agentId>.json` holds a schema version, `traceId`, `agentId`, Bee role, execution mode (`afk` or `hitl`), `taskId` when present, normalized proposal kind, workspace provenance, `baseSha`, summary, sector, byte size, an optional best-effort file count, and capture time. The sidecar also retains the original synthesized event envelope and publication status. Content identity and capture metadata do not change after the record is installed; publication status may be updated atomically. Sidecar makes the record self-describing and survives bus purge. `baseSha` is the captured starting `HEAD`, not a certified patch application base. The sidecar is the archive's own context, not a second timeline: a trail surface reads events from the trail event log (040) and patch bytes from this store, and the envelope held here is retained so the record stays self-describing on its own — it is not merged into event feeds and is not an authority that any surface should consult for ordering, attribution, or completeness.
4. **Naming and retries.** `agentId` is minted per run, so it identifies one synthesized proposal attempt without a counter. Rework and resumed HITL launches get new run ids. The first installed patch is never overwritten: retrying the same finalization reuses the complete existing record and original event, without recomputing a new diff or event timestamp. A conflicting create for that run is an error. Concurrent writers cannot replace each other's bytes. A numeric suffix is reserved for the day a single run may synthesize more than one proposal.
5. **Content is the existing collector's output, with limited attribution.** Preserve the bytes successfully returned by the current diff collector, including its present limitations. Baseline hashes filter candidate tracked files; the generated diff is against the current `HEAD`, not necessarily `baseSha`. Earlier edits within a changed file can be included; untracked files and changes committed before collection can be omitted; deleted files can make collection fail, and renames are not guaranteed. An empty result means only that the collector produced no diff. This spec does not fix those cases or promise exact attribution, binary capture, or reconstruction of a workspace. Collection happens once during successful finalization, after applicable completion checks and the existing `post_exec` hook, and the result is passed to storage and publishing. Collection errors are surfaced as proposal-finalization errors; no empty, partial, or summary-only synthesized proposal is substituted.
6. **Complete record before publication.** Write and close temporary files inside the proposal store, install the immutable patch without replacing an existing file, then atomically install the sidecar as the visibility marker. A normal list entry requires a complete, parseable sidecar and the matching regular patch file with the recorded size. Temporary files and a patch lacking its sidecar are not valid proposal records; partial or corrupt records produce a diagnostic without hiding other valid entries. Retrying may finish a matching orphan patch by installing its missing sidecar, but never overwrites conflicting bytes. Publish the `MUTATION` only after both final files are readable. Failure to prepare the complete record prevents publication of its ref, even when bus connectivity is optional. Comb scan-flush behavior and artifact announcements are untouched. This defines visibility across process interruption, not a stronger guarantee against filesystem loss or power failure.
7. **Execution gate and explicit events.** A new record is prepared only when execution/session completion is successful after applicable completion checks, the effective Bee configuration permits the matching auto-published proposal kind for its workspace, and collection returns a non-empty diff. Failed, cancelled, timed-out, or completion-contract-rejected executions produce no synthesized proposal record. Evaluate the gate from the final status, not just a nil adapter error. An explicitly emitted or queued code proposal for that run suppresses duplicate synthesis; it is passed through unchanged and gets no automatic patch conversion. This archive therefore covers runtime-generated proposals, not every hand-authored `MUTATION`.
8. **Payload contract.** Synthesized proposals carry `ref` = colony-root-relative patch path, and no `diff`; the existing task/workspace provenance fields remain. Proposal validation continues to require at least one of `diff`, `ref`, or `summary`, so the payload stays valid. Only new synthesized refs acquire the path semantics: historical object-store refs remain opaque legacy references, and explicitly authored refs are not reclassified as archive files merely because they appear in a `MUTATION`. Archive listing and export read the local store rather than assuming every event ref is a file.
9. **Object store offload removed.** The size threshold branch, the runtime's artifact-store dependency, and the emptying of `diff` on offload all go away. Bus-level object deletion stays for objects written by earlier versions. A missing or unreachable object store can no longer affect proposals.
10. **Guard task text.** For a new runtime-generated archive ref, the mutation-to-task formatter supplies the proposal summary and the existing workspace context, omitting both the diff block and the archive pointer. Review guidance continues to direct the Guard to the assigned repository workspace. The ref remains in the event for history consumers. Formatter handling of explicit inline diffs and legacy refs remains compatible; the new storage convention is not a reason to drop third-party proposal input.
11. **Export slice.** A new `patches` include token adds a proposal-patches slice to the export payload and its own section in Markdown and HTML, independent of the artifact caps. List all complete records with publication state and content-omission reasons. Bodies are included only within the per-patch and aggregate inline budgets; oversized, unsuitable-for-text, or unreadable entries retain their metadata, ref, and byte size. Use deterministic ordering by capture time, with agent id as a tie-breaker. The slice is filesystem-only and requires no bus. Trails without a patch directory produce an empty slice. An export with omitted bodies is a history report, not a complete portable archive; a local ref does not make an omitted body available offline. Concrete budget values and delivery of omitted originals remain open in Further Notes.
12. **Console surface.** A per-trail proposal-patches listing and content endpoint, with its own preview cap, publication state, and `bytes` value per entry. The listing reads sidecars and file metadata without loading patch bodies. Content endpoints explicitly report omitted or truncated preview content and never label a partial preview as the original patch. Rendered beside the live merge-gate preview as a distinct block, including on a trail whose live worktree is already gone.
13. **Retention and its limit.** No new cleanup command in the agreed baseline: `paseka purge --runs`, `paseka prune --runs`, and per-trace `--all` variants remove the trail run tree, so patches go with it. Existing prune selects whole trails by last activity, not individual patch age. An active Standing Trail can therefore accumulate proposal records without a size or age bound; there is no automatic retention schedule or storage quota implied by this spec. A possible extension for trimming old bodies within active trails is an open proposal in Further Notes.
14. **Prompt context.** The proposal directory, archive refs, sidecar metadata, and patch bodies are not injected into Guard prompts by this feature. The store is runtime-owned and is not offered as a Bee handoff/write target. A proposal record captures collector output at finalization; it makes no assertion about what later existed in the workspace or what a Guard approved.
15. **Backward compatibility.** No migration of historical inline diffs or object-store objects. Trails predating this spec simply have no patch directory and read as empty. Payload validation is unchanged, explicit producers keep working, and bus cleanup retains legacy object deletion. New readers do not turn a legacy object name into a filesystem path.
16. **Publication state and failure handling.** Install a complete record with `publicationState: unpublished`. Immediately before a real broker attempt, atomically change it to `unconfirmed`; after a positive broker acknowledgement, atomically change it to `published`, recording confirmation time. An error or process interruption after an attempt leaves `unconfirmed`, with the last error when available: it must not be presented as definite rejection or cause deletion of bytes that a published event may already reference. A crash before the attempt can conservatively leave `unconfirmed`. A missing publisher or file-only no-op publisher cannot confirm publication and leaves the record `unpublished`. If acknowledgement succeeds but recording it fails, retain the record and report the confirmation-write failure; its on-disk state remains conservatively unconfirmed. Status means what was confirmed at capture time, not that the event is still on the bus after a later purge. Publication-state updates use atomic sidecar replacement while retaining immutable content identity. There is no cross-filesystem/bus transaction or exactly-once guarantee.
17. **Proposal-finalization diagnostics.** Collection, storage, publication, and confirmation-write errors must be visible even when the bus is optional. AFK finalization propagates the error when required and persists a run warning otherwise. HITL teardown persists an equivalent proposal-finalization note readable through the normal session/run outcome surfaces. A successful agent process is not described as a successfully published proposal when finalization failed. Complete unpublished/unconfirmed records remain inspectable and distinct from execution failures, which never reach the preparation gate. A retry reuses the original event; a confirmed record is not republished, and uncertain retries retain the bus's existing at-least-once limitations. No new background retry or reconciliation service is introduced.
18. **HITL is an implementation path, not an existing assumption.** Before starting the PTY, capture the workspace baseline and retain the effective Bee configuration and proposal context used for that launch. On successful session completion, run the shared proposal gate, collector, writer, and publisher after the existing session hooks; this is new work in session finalization, not a call through the AFK dispatcher. Reuse common proposal logic for AFK and HITL without introducing AFK-only summary/completion requirements into sessions. Failed/cancelled sessions skip synthesis. Resume creates a new Paseka run id, captures a fresh baseline, and leaves earlier patch records intact even when the provider session id is reused. Explicit/queued proposals suppress duplicate synthesis as in decision 7. Bus-unavailable sessions may still retain an eligible record as unpublished or unconfirmed; they cannot silently claim publication. No session-specific Console UI is required.
19. **Bytes, previews, and restoration.** Write the collector's original bytes without replacement decoding or newline normalization. Arbitrary diff output is not guaranteed to be valid UTF-8; text surfaces omit unsuitable content with a reason while preserving its size and ref. Binary file entries may contain only Git's textual marker, without the binary contents. No promise is made that `git apply` succeeds, that `baseSha` plus patch recreates the run, or that all repository changes were captured. Preview bodies are escaped text, never interpreted as markup from the patch.
20. **Read bounds.** Inspect file size before allocating a preview body and use a bounded read even after the size check, since a file can change between stat and read. Enforce each surface's body cap and the export's remaining aggregate body budget during reading, not after loading whole files. Apply UTF-8 validation only to bounded content. Listing must not read diff bodies to compute file counts; report the optional captured count or unknown. These requirements bound body reads, not the number of metadata entries or the writer/collector's memory use. Exact limits and additional list/download behavior remain open in Further Notes.

## Testing Decisions

Good tests here assert observable results: a complete record exists at the colony-root-relative path named by the payload ref, its bytes equal the collector output, its publication state is honest about broker confirmation, and nothing is announced or listed as a trail artifact. They do not assume that the diff is a strict per-run delta, reconstructs a workspace, or represents Guard-approved bytes. They do not assert on internal call order, helper names, or the absence of a JetStream call.

Modules under test:

- **Runtime proposal publish** — a complete record for an eligible completed run with non-empty collector output; no record when output is empty or the Bee does not auto-publish proposals; the ref resolves from `ColonyRoot` regardless of consumer cwd; the payload carries no inline diff; two runs of the same Bee produce distinct records. Failed/cancelled/timed-out results and completion-contract downgrades suppress synthesis even when the adapter returned no Go error. Explicit or queued proposals retain their payloads and do not cause duplicate synthesis. Collector errors are visible without publishing a broken or partial replacement proposal.
- **HITL finalization** — successful interactive completion uses the same eligibility and storage rules; hooks finish before the captured diff is finalized; a cancelled/failed session creates no synthesized record; resume with the same provider session gets a fresh baseline and a distinct run/patch; explicit proposal emission suppresses a duplicate; bus absence cannot mark publication confirmed; collection/storage/publication errors are persisted in the session outcome. Use a stub session adapter/PTY lifecycle without a live LLM.
- **Patches store** — write/list/metadata/content round-trip; non-UTF-8 bytes round-trip without mutation; reserved-subdirectory registration keeps the directory out of run listings and timeline event merges; traversal, symlink escapes, and refs into another trail are refused. Incomplete files are excluded with a diagnostic; malformed sidecars do not hide valid records; content and recorded size must agree. Identical retries reuse a record; conflicting writes and concurrent creates cannot overwrite it.
- **Publication failure boundaries** — partial storage failure yields no published ref; a complete record is readable when the publisher observes its event; publisher errors, an ambiguous timeout, and interruption before confirmation leave a retained unconfirmed record; successful acknowledgement marks it published; failure to persist acknowledgement is visible and conservative; nil/no-op publishers leave unpublished records. A confirmed retry does not publish again; retryable attempts reuse the original envelope and immutable body. Use controlled publishers and injected storage failures rather than assuming a broker transaction.
- **Guard isolation and legacy formatting** — synthesized archive refs and patch bodies are absent from Guard tasks/prompts for root/isolated workspaces, with and without sectors; summary and workspace review guidance remain. Legacy/explicit inline diffs and opaque refs preserve their formatter behavior. Tests do not claim the stored proposal equals the later review state.
- **Trail comb isolation** — a proposal run announces only files the run itself wrote to the comb; the patch appears in no artifact listing and no `artifact.written` payload.
- **Export** — the patches slice is absent without the include token; present with it, deterministic and self-describing from sidecars, including publication state; oversized/invalid-text/unreadable entries retain metadata and omission reasons; limits bound actual reads and the aggregate inlined body bytes; no patches directory yields an empty slice and no error; one malformed record does not make valid records disappear; Markdown and HTML escape patch content and identify incomplete exports. Budget boundary tests use the values selected before implementation.
- **Console** — listing returns metadata and sizes without reading bodies; content reads are bounded, including when a file grows after stat; oversized or unsuitable content has an explicit preview result; partial content is not represented as a complete original; records stay readable after worktree removal and bus purge; the merge-gate endpoint is unchanged. Add original-download tests only if that proposal is accepted.
- **Retention** — `purge --runs` and `prune --runs` remove records along with an eligible trail; `purge --bus` leaves bytes and historical publication status on disk. Under the existing policy a recently active Standing Trail retains old patches; tests must not imply an individual-patch TTL or a disk quota.

Prior art in-repo: runtime proposal/publish tests with a fake publisher and stubbed workspace baseline, session lifecycle/resume tests, export include/format tests, runs projections tests for reserved subdirectories, purge and prune tests, and console handler tests for trail-scoped endpoints. Collector limitations are documented compatibility boundaries; testing this archive must not accidentally turn them into stronger attribution or restoration promises.

## Out of Scope

- Side-by-side per-run proposal diff previews in the Reviews screen (tracked as a separate backlog item — [Per-run proposal diff in Reviews](../plans/backlog.md#per-run-proposal-diff-in-reviews)); this spec delivers storage, export, and a listing surface, not a diff UI.
- Compressing, splitting, or paging very large patches for transport, and any object-store tier for patches above a size cap. Patches are stored whole on disk; only inline rendering is capped.
- Instructing Guard Bees to review the stored patch instead of the working tree. Review truth does not move.
- Strict per-run attribution from a dirty baseline; changes to collector handling of committed/untracked/deleted/renamed files; guaranteed capture or restoration of binary contents; a guaranteed-applicable patch; complete workspace backups; or proof/correlation of the immutable state a Guard approved.
- Any change to comb semantics, comb baselines, artifact kinds, or `artifact.written` batching.
- Migrating historical `MUTATION` payloads out of JetStream into patch files, or backfilling patches for trails that predate this spec.
- New automatic retention cadence, retention configuration, or a new prune target in the agreed baseline; patches ride on existing whole-trail run retention. Further Notes records a possible extension, not an approved deletion policy.
- Session-specific patch UX in the Console. Implementing HITL baseline capture and proposal finalization is in scope, and interactive records use the common trail history surfaces.
- Raw bus payload display for `paseka replay` or the Timeline (separate backlog item on runtime-synthesized events).
- Making patches writable by Bees; only the runtime writes them.
- A new background publish-retry/reconciliation service, distributed filesystem storage, or exactly-once bus delivery.

## Further Notes

- Contracts to update when this ships: the code-proposal workspace spec (replace the ">64 KiB → object store" rule for new synthesized proposals), the artifacts protocol (state that the trail comb does not contain proposals), event contracts (new archive refs versus legacy object-store refs), interactive-session guide (new baseline capture and proposal finalization), and the CLI guide (new export include token, limited collector/restoration guarantees, publication states, and whole-trail retention). History and API documentation must describe this as an archive of collector output rather than a record of Guard-approved state.
- New synthesized `ref` values identify local archive paths while their records are retained. Historical object-store refs and explicit producer refs keep their existing meaning. Export and Console read the patch store and do not fetch or migrate those legacy refs.
- **Resolved dependency on [040-trail-event-log](040-trail-event-log.md):** 040 shipped, so the synthesized `MUTATION` now reaches the trail record through the publisher seam and a patch has a position in the trail's event order. This spec deliberately does not write a timeline on its own account — the patch `ref` lives inside the synthesized event, so the row and the patch link appear together as soon as that event is recorded once, which is exactly what the trail event log does. Related backlog items this spec partially answers but does not close: [Per-run proposal diff in Reviews](../plans/backlog.md#per-run-proposal-diff-in-reviews) (the side-by-side diff UI, not the storage, which now ships).
- If best-of-N/swarm execution is added, each separately identified proposal run fits the same naming scheme. This spec does not add a swarm runtime.
- **Preview/export budgets (decided, shipped).** 512 KiB per patch body for Console preview (`patches.MaxPreviewBytes`), 512 KiB per inlined patch body for export (`maxInlinePatchBytes`), and 8 MiB of raw inlined patch-body bytes across one export (`maxAggregateInlinePatchBytes`). These are separate surface limits even when the initial per-file numbers coincide; escaping and report metadata can make the final report larger than 8 MiB. Recent records are preferred for body inclusion, with agent id as the stable tie-breaker, and older/oversized records are listed with explicit omission reasons.
- **Open decision — originals and offline packages.** A streamed original-download endpoint would let the Beekeeper retrieve the retained bytes without raising the preview cap or buffering the complete file. It would not guarantee a reconstructable workspace or make a report containing only a local ref portable. A complete offline package containing originals could be a separate export mode; it is not assumed in the current report contract. Download/package scope is still awaiting a decision. Metadata pagination/limits for very long trails and collector/write-path memory bounds are separate concerns; the body budgets alone do not solve them.
- **Open decision — active Standing Trail history.** Keeping the existing whole-trail prune policy for the first version is viable if indefinite growth on an active trail is an accepted limitation. It avoids deleting history as a side effect of completing a run. If storage use later warrants a bound, a proposed extension is to let the existing `prune --runs` trim patch bodies by each record's capture time (for example, older than 30 days), even while the trail remains active; preserve sidecars with an explicit `bodyStatus: expired` and show that reason in Console/export instead of reporting corrupt/missing storage. Checkpoints and other comb contents would remain outside that trimming operation. Such pruning would run only when invoked, not on every write, and time-based pruning alone is not a hard byte quota. The TTL, trim eligibility, and expired-body semantics are not agreed implementation decisions in this spec; metadata growth would still need a separate policy if a strict disk bound became necessary.
