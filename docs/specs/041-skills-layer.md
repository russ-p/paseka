# Spec 041: Skills layer

## Status

**(Approved)**
The colony owns a skill store, Bees declare which skills they may use, the runtime resolves and delivers them, adapters report what was used, and the Archivist Bee can propose a new skill that a Beekeeper approves. Design settled in review and approved for implementation.

The store has one root: `.paseka/skills/` in the repository. An earlier draft also carried a machine-local root, `shared:`/`local:` tier prefixes, shadowing, and a `move` verb between the two; that is withdrawn (decision 1). The gate is committed by default, and a profile may override the selection (decision 3) but never adds a procedure from outside the store. Client discovery directories are not the store: they stay client-owned, and the trail configuration captures `.agents/skills/` for reproducibility without this layer gating it (decision 1).

Scope of this spec is the whole layer — store, selection, delivery, attribution, proposal — described as four phases in Further Notes. Phase 1 (store, selection, delivery, run record, `load`, and the store commands) is the implementable core; Phases 2–4 (attribution and export, proposal and approval, native client bridge) build on it.

Five amendments (A1–A5) are proposed below in response to [the self-improving-colony brief](../idea/self-improving-colony.md): a second delivery mode, the `load` verb, skills in a portable pack, the phase list that follows from them, and approval into a trail's configuration for a trial.

## Problem Statement

A Bee that does generic work well still does this colony's work badly, because the colony's procedures live only in a Beekeeper's head and in prompt templates. The Beekeeper writes a procedure down once, in the best place available — the role's prompt template — and from then on it is unconditional, unconditional per role, and grows without bound. There is no way to say "this procedure applies to the release task and to nothing else", no way to hand the same procedure to two roles, and no way to know which procedure a given run actually used.

The industry has converged on a format for exactly this. The Agent Skills specification defines a portable directory — a `SKILL.md` with YAML frontmatter plus optional `scripts/`, `references/`, and `assets/` — and the major clients already read it. Cursor discovers skills from `.agents/skills/`, `.cursor/skills/`, `~/.agents/skills/`, and `~/.cursor/skills/`. OpenCode discovers them from `.opencode/skills/`, `~/.config/opencode/skills/`, `.claude/skills/`, and `.agents/skills/`, and additionally accepts an explicit list of skill directories in its config. Claude Code reads `.claude/skills/` and `~/.claude/skills/`. The format is portable, the clients are ready, and Paseka has no story for it.

Every existing workaround is bad in a different way, and all of them fail in Paseka's terms rather than the client's.

**A skill dropped into a client directory is outside the colony's control.** It is loaded by the client, so the Bee may use it, and the trail configuration does capture its bytes at trail start ([spec 042](042-trail-fork.md)) — so the file is not literally unknown. What the colony cannot do is act on it: the Bee's config does not list it, so no Beekeeper reviewing a change can see that this role now carries a procedure, nothing can withhold it from a role that should not have it, and the colony cannot answer "which skills did this run have" — so a trail export cannot show it, and the trail's history cannot be compared against the skills that were on offer. A configuration that is captured but neither gated nor reviewed for a role is not managed configuration, and the whole point of a colony is that its configuration is reviewable and its effect is attributable.

**A skill dropped into a client directory cannot be gated.** The client advertises every skill it discovers to every agent it starts. The one thing Paseka needs most — that a procedure reaches the Bees that should have it and no others — is exactly the thing the client cannot express. A procedure meant for one role and one meant for the whole colony are indistinguishable to the client.

**Paseka's own configuration is not a discovery path for any client.** A Bee that runs under Paseka is an external CLI in a working directory, and that CLI looks for skills in its own conventions. The colony's manifest, the Bee configs, and the prompt templates are invisible to it. So a skill that *is* under the Beekeeper's control — in the repository, in a diff, in the code review — is a skill the Bee cannot see, and a skill the Bee *can* see is one the Beekeeper cannot review. The two sets do not intersect, and Paseka currently offers no way to make them intersect.

**Nothing records what a Bee was given.** A run's record holds the prompt, the system prompt, the model, and the token usage. It does not hold the reusable procedure packs that were on offer, and certainly not whether any of them was used. A Beekeeper auditing a trail cannot tell the difference between a Bee that followed the release procedure and one that improvised, because the release procedure is not in the trail at all.

**A repeated failure has nowhere to become a procedure.** The colony already has an Archivist Bee whose whole job is to read a finished trail and write down what should be remembered — the deferred work, the review notes that were never applied, the merge lag. It sees the recurring shape of a colony's friction constantly. It has nowhere to put a procedure when it sees one, because the store does not exist, and because a procedure that a Bee wrote must not be able to install itself into the Bees that will later obey it.

## Solution

Give the colony a skill store it owns, and make every step of a skill's life a colony step.

**The store is the colony's.** A skill is a directory in the Agent Skills format, held in one root inside the repository (`.paseka/skills/`), version-controlled and reviewed like any other colony configuration. It is spec-shaped, so a skill written for Paseka is readable by any client that speaks the standard, and a skill written elsewhere can be dropped in by hand.

**Selection is the colony's.** A Bee's configuration lists the skills it may use. The list is a gate, not a hint: a skill that is not listed for a Bee does not reach that Bee, no matter what any client would find on disk. A Bee that declares no list and inherits no default gets nothing; a Bee that declares an empty list opts out of the colony default. A Bee's list replaces the colony-wide default rather than adding to it, because "remove this procedure from this one role" has to be expressible. A list entry is a name, a family pattern, or `*` for every active skill.

**Delivery is the runtime's, the mechanism is the adapter's.** The runtime resolves the effective skill set for a run from the trail's frozen configuration and hands it to the adapter. The adapter knows how its own CLI takes instructions and is responsible for making them available. The first delivery mechanism is deliberately universal: the runtime renders the skill metadata — name, description, and where the file is — as a distinct section of the run's system prompt, after the role's own instructions, which is the same shape the clients themselves advertise, and which works for every adapter including the ones with no skill support at all. The delivery mode and the effective set may be overridden by a profile, so a local model can receive less context without changing the committed colony. The client-native mechanisms, where a client can be pointed at a directory of skills directly, are a later phase and are additive.

**Use is recorded.** The runtime records which skills a run was offered. Adapters that can see what their CLI actually did report which skills were used, and the trail export carries both — so a Beekeeper reading a trail can see the procedures that were on offer and the ones the Bee reached for.

**A proposal is a proposal until a human approves it.** The Archivist Bee can read a finished trail, recognise a procedure worth keeping, and write it out as a proposal artifact. It publishes a discovery saying a skill was proposed. It cannot write into the store, and nothing installs a proposed skill on the colony's own initiative. The Beekeeper reviews the proposal, and the runtime — never the Bee — validates and installs it. Approval makes a skill *available*; it does not make it *active*, because activation is the per-Bee list, which is reviewed in the repository like everything else. A trial on one trail (A5) is the deliberate exception: it writes that trail's pinned role list and nothing else.

The properties that make this safe rather than merely convenient:

- **Approval and activation are separate.** A skill the Beekeeper approved sits in the store until a Bee's configuration lists it. The blast radius of a bad skill is the set of Bees that opted in, and that set is visible in a diff. A trial on one trail is the deliberate exception, and it writes only that trail's pinned role list.
- **The proposer never writes the store.** The Bee writes a proposal artifact into the trail's comb; the runtime writes the store. A Bee that gets confused, or manipulated, cannot install instructions for its successors.
- **A human approves.** There is no auto-approval path, for the same reason there is no path by which a run promotes itself.
- **Provenance is durable.** An installed skill records where it came from — the trail that proposed it, who approved it, and when — so an approved-but-surprising skill is explainable later.

## User Stories

1. As a Beekeeper, I want to write a procedure once as a skill and use it in any Bee, so that the same knowledge is not re-explained per role.
2. As a Beekeeper, I want a skill to live in the repository, so that it is version-controlled, reviewable, and shared with my team.
3. As a Beekeeper, I want a Bee's configuration to list the skills it may use, so that the procedures a role carries are visible in the diff that changes it.
4. As a Beekeeper, I want a Bee that declares an empty list to receive none, so that a role never silently inherits procedures it did not ask for.
5. As a Beekeeper, I want to remove a procedure from one role while leaving it in others, so that a skill is not all-or-nothing for the colony.
6. As a Beekeeper, I want a colony-wide default skill list that roles inherit unless they override it, so that a common procedure is declared once.
7. As a Beekeeper, I want to opt a role out of the colony-wide default explicitly, so that the difference between "inherits" and "declares an empty list" is readable.
8. As a Beekeeper, I want one role to be able to list a family of skills by pattern or every active skill with `*`, so that a growing set of related procedures is not re-listed per role and a catch-all role does not go stale.
9. As a Beekeeper, I want a profile to select a different skill set or delivery mode for a model or adapter, so that a local model is not given context it cannot use.
10. As a Beekeeper, I want a malformed skill to be reported with its name and the reason, so that a typo in frontmatter does not silently disable a procedure.
11. As a Beekeeper, I want `doctor` to report a role that references a skill that does not exist, so that a rename cannot leave a role silently skill-less.
12. As a Beekeeper, I want `doctor` to report a skill that exists but does not satisfy the format, so that a broken procedure is visible before a Bee needs it.
13. As a Beekeeper, I want to list every skill the colony can see with its description, validity, and the roles that carry it, so that I know what is on offer without reading directories.
14. As a Beekeeper, I want to see one skill's resolved file location and content, so that I can read exactly what a Bee would be told.
15. As a Beekeeper, I want a run's record to name the skills that were on offer, so that a trail tells me what procedures the Bee had.
16. As a Beekeeper, I want a run's system prompt on disk to contain the advertised skill block, so that what the Bee was told is auditable, not reconstructed.
17. As a Beekeeper, I want a trail export to list the skills each run was offered, so that an offline report is self-describing.
18. As a Beekeeper, I want a trail export to list the skills each run actually used, so that I can see which procedures earned their place.
19. As a Beekeeper, I want an export to carry the body of a used skill, so that the exported trail still explains itself months later.
20. As a Beekeeper, I want the export to say plainly that usage could not be determined for a run, so that absence of evidence is not read as absence of use.
21. As a Beekeeper, I want the Archivist Bee to be able to propose a skill after reading a finished trail, so that a recurring failure becomes a procedure instead of a memory.
22. As a Beekeeper, I want the proposal to cite the runs, files, and events that motivated it, so that I can judge the evidence rather than take the claim on faith.
23. As a Beekeeper, I want to review a proposed skill in the console or the shell, so that approving it is a deliberate act.
24. As a Beekeeper, I want to approve a proposed skill into the store, so that it becomes part of the colony.
25. As a Beekeeper, I want to trial a proposed skill on one trail before sharing it, so that I can measure it without changing the store.
26. As a Beekeeper, I want approval to be refused by default and to require my action, so that a Bee can never install instructions for its successors by itself.
27. As a Beekeeper, I want a skill approved into the store to stay inert until a role lists it, so that approving is not the same as deploying.
28. As a Beekeeper, I want an approved skill to record which trail proposed it and that I approved it, so that a surprising skill is explainable later.
29. As a Beekeeper, I want to be told which roles reference a skill before I remove it, so that a removal does not silently strip a procedure from a role.
30. As a Beekeeper, I want to disable a skill without deleting it, so that I can neutralise a bad procedure and keep its history.
31. As a Beekeeper, I want the console to show that a skill was proposed rather than hand-written, so that I read it with the right suspicion.
32. As a Beekeeper, I want a skill to be usable by a script Bee, so that a non-LLM step can read the same procedure the LLM steps read.
33. As a Beekeeper, I want a script Bee to receive the resolved skill set as data, so that it can use it without knowing Paseka's internals.
34. As a Beekeeper, I want the skill block to stay small and bounded as skills are added, so that adding procedures does not quietly inflate every prompt.
35. As a Beekeeper, I want skill bodies loaded only when a Bee actually needs one, so that a large procedure does not sit in every run's context.
36. As a Beekeeper, I want a Bee's use of a skill to be visible on the run, so that I can tell a procedure that works from one that is never reached for.
37. As a Beekeeper, I want an interactive session to report skill use the same way an unattended run does, so that HITL and AFK trails are comparable.
38. As a Beekeeper, I want a run's advertised skills to be recorded even when nothing used them, so that "offered and unused" is a finding rather than a silence.
39. As a colony author, I want skills to be portable to another client, so that a procedure I wrote is not trapped inside Paseka.
40. As a colony author, I want a skill written for another client to be usable in Paseka, so that the standard is not a one-way door.
41. As a colony author, I want a skill directory to carry its supporting files, so that a procedure with a script or a reference template is a unit.
42. As a colony author, I want a skill's declared name to be checked against its folder, so that a rename is visible and errors are legible.

53. As a maintainer, I want a role's completion contract to be able to differ per intent, so that a role with two kinds of output can require the right one for each.
54. As a maintainer, I want the store to be a plain directory of plain files, so that it survives every tool in the chain — git, diff, an editor, a file browser.
55. As a maintainer, I want the skill block rendered in one place, so that every adapter advertises skills identically.
56. As a maintainer, I want the store to be excluded from the trail's run tree, so that cleanup of run data does not touch it.
57. As a Beekeeper, I want a single `paseka skills` command group, so that every operation on a procedure is one place.
58. As a Beekeeper, I want `paseka skills list` to show every skill the colony can see with its state, so that I know what is on offer.
59. As a Beekeeper, I want the listing to name the roles that carry each skill, so that I can see the gate at a glance.

## Implementation Decisions

1. **One root, in the repository.** A skill lives under `.paseka/skills/` in the colony configuration in the repository, next to bees, prompts, and cues. It is version-controlled and reviewed like every other colony file, and a trail freezes it, with its ledger, in its configuration snapshot ([spec 042](042-trail-fork.md)). There is no machine-local root: the role gate is a committed list by default, and although a profile may override the selection (decision 3), it can only choose among procedures that are in the committed store. A skill whose availability depends on the machine that runs a Bee makes a trail unreproducible. Paseka also has no supported mode in which the colony configuration lives outside the repository, so a machine-local root would have no reviewed place to declare its skills. The machine-local bee overlay (`bees/<role>.local.yaml`) therefore does not carry skills, so the gate never depends on the host; a `skills` key there is a load error rather than a silent no-op, because a profile is the supported per-machine override (decision 3).

   The store is not a client discovery directory. The paths a client reads on its own — `.agents/skills/`, `.cursor/skills/`, `.claude/skills/`, and the client's home equivalents — stay client-owned. The trail configuration captures `.agents/skills/` as a configuration input for reproducibility, and `doctor` and validation see it, but this layer neither gates, advertises, counts, nor attributes what a client discovers there. A skill a Beekeeper wants gated is copied into the store and listed for a role.

2. **A reference is a name or a pattern, and there is one namespace.** A reference may be a bare name or a name pattern; there is no tier prefix. The earlier draft's `shared:`/`local:` form existed only to disambiguate two roots, so with one root it is dead syntax. A `shared:foo` or `local:foo` reference names something that cannot exist and is reported as an invalid reference rather than resolved.

3. **A role's list replaces the colony default; it does not extend it.** The colony manifest carries an optional default list at `defaults.skills`, and a Bee's configuration carries its own at `skills`. When a Bee declares a list, that list is the whole set for that Bee; the colony default does not apply. Merging would make "this procedure must not reach this role" unexpressible, and the per-role gate is the property the whole layer exists to provide.

   The absence case is therefore tri-state and is treated as such: a Bee that omits the field inherits `defaults.skills`, a Bee that declares an empty list opts out of it explicitly, and a Bee that declares a non-empty list uses exactly that list. The schema must keep "absent" distinct from "empty", and a plain string slice cannot, so the loader uses a presence-aware field. An explicit empty list is easy to lose in a diff, so `doctor` reports it as a warning; it is a legitimate opt-out, not an error.

   A list entry is a name, a family pattern, or `*` (decision 23). A profile ([spec 027](027-config-profiles.md)) may override `defaults.skills` and a role's `skills`; the same tri-state applies in a profile (absent leaves the lower layer, an empty list opts out, a list replaces), and a home profile wins over a colony profile, which wins over the committed value, matching spec 027's precedence. The selected profile is part of the trail's frozen configuration ([spec 042](042-trail-fork.md)), so the effective set is reproducible, and a profile changes which committed procedures a role receives rather than adding a procedure from outside the store. A home profile's `config.yaml` is captured as a private input when it carries these fields. `skills` in `<role>.local.yaml` is a load error, not a silent no-op: a profile is the supported per-machine override, and a misplaced key must not look like a gate. The layer that set the effective list — committed, colony profile, or home profile — is reported like any other launch field.

4. **No declaration anywhere means no skills.** With neither a colony default nor a role list, a Bee receives nothing. A procedure is executable content with a context cost, so the default is the safe one, and the cost of opting in is one line in a reviewed file.

5. **The store holds spec-shaped directories, one per skill.** A skill is a directory under `.paseka/skills/` named for the skill, holding a `SKILL.md` with YAML frontmatter and a Markdown body, and optionally `scripts/`, `references/`, and `assets/` subdirectories holding its supporting files. Nothing in the format is Paseka-specific, so a skill moves to another client unchanged, and a skill authored elsewhere moves in unchanged.

   The store is flat: one directory per skill, no category folders. Clients differ on whether they recurse into a skills root, but a flat store is read identically by every one of them, and a category hierarchy is a naming convention, not a capability.

6. **Validation is a load-time gate, it is fatal, and it is the same validation on every path.** A skill is valid when its name is present, matches the standard's shape (lowercase letters, digits, and hyphens, no leading or trailing or doubled hyphen, at most 64 characters), equals the name of the directory that holds it, and carries a non-empty description within the standard's bound (1–1024 characters). A skill that fails validation is reported with its name and the reason and makes the configuration that needs it invalid: a run whose effective set contains it does not start, a candidate configuration that contains it is refused, and `doctor` reports it as an error.

   The same validation runs when the repository store or a trail's frozen copy is scanned, when a proposal is approved, when spec 042 validates a candidate configuration, and when `doctor` runs. A second copy of these rules would drift, so there is one rule set and one report shape.

7. **Resolution is pinned to the trail's frozen configuration; delivery belongs to the adapter.** For a run, the runtime computes the effective skill set from the trail's configuration snapshot ([spec 042](042-trail-fork.md)) — the skill files captured under `.paseka/skills/`, the ledger captured with them, and the role's list from the same snapshot — and never from the live repository store. An edit to the store after trail start therefore does not change a running trail; it reaches a trail only through spec 042's explicit configuration application, and a missing or corrupt snapshot blocks instead of falling back. The shell's inventory commands (`list`, `show`, `validate`) resolve against the repository store because no trail is in scope, and `load` takes the run's identifiers so it resolves the same pinned input the run did. It is one resolver and one rule set; the only difference is which copy it is given. A dispatch whose effective set is invalid — a missing or invalid reference, a pattern that matches nothing, or a budget breach — does not start the adapter.

   The adapter owns the question "how does my CLI receive these", because only the adapter knows the CLI. Resolution runs before the system prompt is rendered, so the advertisement and the launch request are built from one resolved set. The seam is a small set of skill references carried on the launch request, plus the rendered advertisement the adapter may deliver. Adapters that speak a client's native skill mechanism use the references; adapters that do not fall back to the rendered advertisement. Adding a client touches the adapter and nothing else.

8. **The first delivery mechanism is a system-prompt advertisement, appended as its own section.** The runtime renders the resolved skills as a distinct section — a heading plus each skill's name, description, and absolute path to its `SKILL.md` — and appends it after the run's rendered system template. The section is never written into a template file: templates render the role's instructions, and the runtime owns the block. When a Bee has no system template, the section is the whole system prompt. This is the same shape the clients themselves use to advertise skills to a model, and it is the only mechanism that works for every adapter, including a script Bee and a client with no skill support.

   The advertisement carries metadata only. Bodies are never inlined: the standard's progressive disclosure exists so that a procedure costs a small fixed amount until it is needed, and a runtime that inlined bodies would destroy that property. The Bee reads the file when the task calls for it.

   The section is rendered in exactly one place — the one function both the unattended dispatcher and the interactive session manager call to render a system prompt — so every adapter advertises identically. The runtime writes the composed result to the run's system-prompt file before the adapter starts, so an adapter that never writes it — a script Bee — still has the same auditable file. The advertised path is the file's location in the trail's frozen configuration, so a running trail keeps reading the bytes it started with.

   Placement delegation is deliberately deferred. A later phase may expose the section to the template engine as an optional construct that renders the same block and reports that it consumed it; the runtime then appends the section only when the template did not. There is no setting that turns the advertisement off, because a role that lists a skill and does not receive it is the silent failure the gate exists to prevent.

   The advertisement is fixed when the run or session is created. A resumed provider session keeps its first turn's context, so the section is already there; the runtime does not re-inject it. A configuration application does not change an existing session, and a new attempt or a new session gets a new advertisement, so the offered set is stable for the life of a run.

9. **The run record carries what was offered.** The run's request record gains the names of the resolved skills, alongside the model and the model alias that are already recorded there for the same reason: the run's configuration is fixed at dispatch and must stay readable after the configuration changes. The record already carries the configuration reference, so a reader can locate the frozen bytes the names were resolved from. The record is written by both the unattended dispatcher and the interactive session manager, so an AFK run and a HITL session carry the same field. The advertisement itself is preserved in the run's system-prompt file, not reconstructed from the request record.

10. **Usage is an optional adapter capability, mirroring the existing session-log capability.** An adapter that can read its client's transcript may report which skills the run used. The result is a list of uses, each with a skill name and the evidence for it — the client's own skill invocation, a read of the skill's file, or a run of a bundled script. A capability that is not implemented reports that plainly, in the same way the existing session-log resolver reports an unsupported provider, so a missing measurement is visible rather than read as a negative result.

    Attribution reuses the tool-call reading that already exists. A generic pass matches the paths in tool-call arguments against the resolved skill locations in the trail's frozen configuration, which attributes a use for any client whose tool calls are already being read, without a client-specific rule. A client-specific refinement may be added later; it does not change the shape.

11. **The export carries both sides.** A new export section lists, per run, the skills that were offered and the skills that were used, and includes the body of each used skill so that the exported trail still explains itself. The offered set, the use evidence, and the body are read from the trail's frozen configuration, so a later store edit or removal does not change what an old export says. A run whose usage could not be determined says so in the same place, using the capability's own omission reason.

12. **A proposal is a bundle of files in the trail's comb, a discovery of its own kind, and a decision beside it.** The Archivist Bee writes the proposed skill — its `SKILL.md` and any supporting files — into the trail's artifact comb, next to the report it already writes, and publishes an `INSIGHT/skill.proposed` discovery carrying the skill's name, description, the reason, the comb reference to the bundle, and the bundle's procedure-content hash (decision 17).

    The comb is used because it already is where a Bee's output goes, it is already announced and visible in the console, and it is already part of the trail's history. The proposal travels with the trail that motivated it, and deleting the trail deletes the proposal.

    The runtime — never the Bee — records what was decided about a proposal in a reserved runtime-owned `.paseka/runs/<trace>/skill-proposals/decisions.ndjson`, one line per decision carrying the skill, the trail, the content hash, the destination, the decision, and when it was taken. The decision lives with the proposal it decides, not in the committed store ledger.

    A dedicated kind rather than a general note is required because a proposal has a machine-readable shape and a lifecycle — it can be approved — and because the role's completion contract has to be able to demand it.

13. **A role's completion contract can differ per intent.** The Archivist Bee has two output kinds after this change — a note and a proposal — and the contract that checks the run's events must demand the right one for the intent that ran. The contract therefore accepts an optional per-intent override, with the role's own contract as the default. This is a schema extension to the Bee configuration, not a special case in the runtime, because the next role with two kinds of output will need it too.

14. **Only the runtime writes the store.** A Bee writes a proposal into the comb and publishes a discovery. Nothing else writes into the store. Installation is a runtime operation, invoked by the Beekeeper through the shell or the console, and it validates before it copies.

15. **Approval is a human act with no automatic path.** There is no policy, flag, or colony setting by which a proposal installs itself, and no path by which a run promotes itself. The argument is the one the whole layer is built on: a skill is instructions that later Bees obey, so a path from a Bee's output to the store is a path from a Bee to the control plane. The Beekeeper is a first-class participant in this colony, and this is the decision they are entitled to make.

16. **Approval installs; it does not activate.** An approved skill is available. It reaches a Bee only when that Bee's configuration lists it. This keeps the blast radius of an approved skill inside the repository diff that a Beekeeper reviews, and it means an approval can be made before anyone has decided who should carry the procedure. A trial (A5) is the deliberate exception: it writes the role list in one trail's pinned configuration, because a trial no role carries would measure nothing. It changes neither the store nor any other trail, and applying a previous snapshot reverses it.

17. **Installation is validated, refuses to overwrite, and records provenance.** The installer runs the same validation as a store scan, refuses to replace an existing skill without an explicit override, and writes a provenance record into the skill's own metadata: the source (`proposal` or `nuc`; a skill with no provenance record is `hand`), and for a proposal the trail that proposed it, the role that proposed it, the approval time, and a content hash. The metadata is string-to-string, as the standard requires, so provenance does not make the skill non-portable; a `nuc` install has no trail or role and omits them.

    The content hash is computed over the procedure content — the `SKILL.md` body and the supporting files, in a stable order, excluding the frontmatter that carries provenance — so writing provenance cannot change the hash. It identifies the approved procedure, lets `doctor` detect a hand edit to the body or a bundled file, and distinguishes two proposals of the same name with different content. It is not the value in the load record (A2), which hashes the served `SKILL.md` bytes: one identifies what was approved, the other what a run opened.

18. **The committed ledger records only what a skill file cannot: the store's enabled/disabled state.** It is one file beside the store, `.paseka/skills.index.json`, not a directory inside it, so a directory under the store is always a skill and never a bookkeeping file a client might load. It carries a schema version and, per skill name, the disabled record — when and why — and nothing else. Provenance stays in the skill's own metadata and the inventory is the directory listing, so each fact has one source and there is no mirror to reconcile. A missing ledger is an empty ledger; a corrupt one fails the mutating commands and `doctor` rather than being silently replaced. It is committed with the store and frozen with it in a trail's configuration snapshot.

19. **Removal and neutralisation are separate.** A skill can be removed from the store, and it can be disabled without being removed. Removal reports the roles that reference it before it happens, so a removal cannot silently strip a procedure from a role. A disabled skill stays in the store and in the ledger, with its history, and is never offered. `remove` deletes the store entry and its state record but not the trail decisions about it; `enable` clears the state record.

    A role that still lists a disabled skill is not a configuration error. The disable is the Beekeeper's own recorded decision, so the skill is skipped and `doctor` says which roles still list it. Making the referencing roles fail would turn an emergency stop into a colony-wide outage; making the skip silent would hide the decision, and the ledger is what makes it visible.

20. **The store is a plain directory of plain files, outside every ephemeral area.** It is not inside a trail's run tree, not inside a worktree, and not inside any cache. Trail cleanup, worktree cleanup, and cache purging leave it alone. It is plain files in a repository, so git, diff, an editor, and a file browser all work on it without the colony knowing.

    A trail's frozen copy under its configuration snapshot is trail data, not the store: it is read-only for the run and is removed with the trail's other retained evidence.

21. **A script Bee receives the resolved skills as data.** The script adapter is given the skill set as a manifest — the same names, descriptions, and locations the advertisement carries — through the process environment the script adapter already passes, and the paths are absolute so the script does not need to know where it was started from. In `command` mode the prompt advertisement carries no path (A1), but the environment manifest still carries the frozen absolute locations, so a script Bee never depends on `load`. A script Bee that ignores the manifest is unaffected.

22. **Budgets are explicit and small, and a breach is a configuration error.** A role may not be offered more than 32 skills, a single file in a skill directory (the `SKILL.md` or a supporting file) may not exceed 256 KiB, and the store's total size may not exceed 8 MiB; the ledger beside the store is not counted. The reason is context, not disk: the standard prices an advertised skill at a small number of tokens, and that price is only acceptable while the count is bounded. Exceeding a limit is reported and makes the configuration invalid: a run whose effective set breaches the role or file limit does not start, and `doctor` and `validate` fail on the store-wide bound. A breach is never resolved by silently dropping a reference. The values are fixed constants, not colony settings: a profile may reduce the set a role receives, but it cannot raise the budget.

23. **The pattern form is a glob over the skill's own name, and `*` alone means every active skill.** A role may list a family of skills by pattern, so a growing set of related procedures is not re-listed per role. The only wildcard is `*`, which matches any run of characters: `paseka-*` selects a family, and bare `*` selects every active skill in the store. `?`, `[]`, and `{}` are not wildcards and are not valid in a skill name, so they are rejected rather than read literally. Patterns match the name declared in the skill's metadata, and the resolved set is deduplicated and sorted by name. A pattern that matches nothing is a configuration error, except bare `*`, which is allowed to match an empty store. `*` expands to every directory in the store except the disabled ones, and an invalid entry under it makes the run fail: the wildcard declares the whole store as that role's gate.

    A pattern is a selection, not a procedure. `validate` accepts one because it only reads a set; `load`, `show`, `remove`, `disable`, `enable`, `approve`, and `reject` act on one procedure and refuse a pattern.

24. **The native client bridge is a later phase, and its shape is already known.** Cursor, OpenCode, and Claude Code each discover skills from client-specific directories, and OpenCode additionally accepts an explicit list of skill directories in its configuration. A native bridge would make the selected set discoverable by the client itself, which buys the client's own skill invocation and command affordances, and costs the colony the gate unless the bridged directory contains only the selected skills. The bridge is therefore a directory of links containing exactly the resolved set, placed where the client looks.

    It is deferred because the advertisement already delivers the set to every client, including those with no skill support, and because the bridge has to answer a question the colony cannot yet answer well: where to put a directory of links in a role's working directory without leaving files behind in the Beekeeper's repository. In a worktree the answer is obvious; in the repository root it is not. Approval, trial, and the store layout do not depend on the bridge: it changes where a client discovers the resolved set, not what is stored or approved.

25. **The Archivist's skill intent is a new intent, triggered by hand.** The role gains an intent for proposing a skill, discovered the way a role's intents are discovered, with its own mission guidance. It is run deliberately, against a named trail, rather than automatically on every finished trail: a proposal needs a human to look at it anyway, and a colony that proposed a skill after every flight would train its Beekeeper to ignore proposals.

    The intent changes what the role is allowed to do. Under the note intent the role writes one report and publishes one discovery; under the skill intent it writes a proposal bundle and publishes a proposal discovery. The role's rules state that it writes only inside the comb, and never into the store, in both cases.

26. **One command group, `paseka skills`, with one verb per thing a Beekeeper does with a procedure.** The group is `list`, `show`, `validate`, `proposals`, `approve`, `reject`, `remove`, `disable`, `enable`. The group is a namespace, not an action: invoking it bare prints its help rather than guessing which of the nine the Beekeeper meant, because five of them change the store and picking the wrong one is not a harmless mistake.

27. **The reference syntax is the same in the shell as in a role's configuration.** A reference may be a bare name or a pattern, and it means the same thing wherever it is written. One syntax and one resolver, so a Beekeeper does not learn a second dialect in the shell, and so a command cannot disagree with the runtime about what a name refers to.

28. **Listing is a table whose state column is a verdict.** The columns are name, state, roles, description. The state is one of `ok`, `invalid`, or `disabled`: an invalid one carries the reason, and a disabled one says so in the same column. The roles column names the roles whose resolved set contains the skill; a role whose list uses `*` or a matching pattern is named for every skill it resolves to, because that is what the gate actually does.

29. **Reading one skill is a different command from reading the store.** `show` resolves a single reference and prints its metadata, its provenance, and its body; `list` is the inventory. `show` can also print only the resolved path, so a script can consume the result without parsing prose.

30. **Validation is a command that can fail a pipeline.** `validate` checks one reference or the whole store and exits non-zero when something is invalid, so it can be a pre-commit hook. A reference may be a pattern, including `*`, and a pattern that matches nothing is itself the failure. Its verdict is the same verdict the store scan and the approval path produce, because it is the same rule set rather than a second implementation.

31. **A proposal is found before it is approved, and it lives with its trail.** `proposals` scans the trails' run data: a `skill.proposed` discovery with no decision is `pending`; a decision makes it `installed`, `refused`, or `trialled` with the destination trail; a discovery whose bundle has disappeared is `missing` and reported rather than hidden. A decision is keyed by destination, so a trial and a store install can both be recorded and the newest decision for each destination is the one shown. Each row names the trail, the skill, when it was proposed, and when it was decided. Nothing about proposals is stored in the committed store ledger, so deleting a trail deletes its proposals and their decisions, and a decision is machine-local because `.paseka/runs/` is not shared through git.

32. **Approval names one or more proposals and installs them in one destination.** `approve` takes one or more references; a reference is `name` or `<trail>/<name>`, and `--trail` supplies the default trail for bare names, so an ambiguous name is an error that names the candidates rather than a guess. The destination is the store by default, because the gate that decides who carries the procedure is the role list (committed, or a profile's override) and not the approval; `--into <trace>` writes the same skills into that trail's candidate configuration instead, as a trial (A5). A batch is atomic: every bundle is validated and hashed before anything is written, so one invalid or conflicting skill writes nothing. In the store, an existing skill of the same name is refused without `--force`; in a trail, the same rule set validates the candidate and the apply is refused before it is queued.

33. **Approval reports the repository consequence and never commits.** Installing into the store leaves an untracked file in the working tree, and the command says so, names the path, and says that the commit is still the Beekeeper's. A trial writes a new configuration revision in the trail and reports the revision and its diff; it touches neither the store nor the working tree. Neither path writes a commit on the Beekeeper's behalf, for the same reason neither approves a proposal by itself.

34. **A refused proposal is recorded with the trail, not in the store.** `reject` appends a `refused` decision to the source trail's `skill-proposals/decisions.ndjson`, keyed by the trail, the skill, and the bundle's procedure-content hash (decision 17), with an optional reason. The refusal is terminal for that exact proposal: it cannot be approved or trialled, the same bundle is not offered again while the trail exists, and a new trail or a changed bundle is a new decision. The record is machine-local with the rest of the trail's run data and disappears when the trail does.

35. **Removal and neutralisation stay separate commands, because their consequences differ.** `remove` deletes a skill and refuses while roles still reference it unless forced; `disable` keeps the skill, keeps its history, and records that it is not to be offered. `disable` records in the state file, `remove` deletes the store entry and its state record, and both name the roles whose resolved set changes, so an emergency stop shows its blast radius without touching the trail decisions about the skill.

36. **Every destructive or terminal command can be previewed.** `approve`, `reject`, and `remove` accept a dry run and print the plan — what would be written, what would be deleted, which role configurations would change — without touching the store. The store is a reviewed artifact, so a command whose mistake is only visible in a diff must be able to show its intent first. `disable` and `enable` are the deliberate exception: they flip one reversible state and undo each other, they name the roles whose resolved set changes, and a preview would only add a step to the emergency stop that `disable` exists to be.

37. **The read commands speak JSON on request; the mutating commands speak in prose.** `list`, `show`, and `proposals` emit a machine contract on request, for a script or another tool. The mutating commands are read by a person deciding something, and a person's reading of "installed into the store, working tree has one new file" should not be a JSON document. `load` is the exception among the reads: it has a side effect on the run's own record and prints a body for a model, so it speaks prose (A2).

## Amendments

The five amendments below are proposed in response to [the self-improving-colony brief](../idea/self-improving-colony.md) and [spec 042](042-trail-fork.md). They amend decision 8, decision 26, decision 32, one out-of-scope item, and the phase list. Each is additive to the settled design: A1 keeps decision 8's path form as the default and adds a second form, and A5 keeps decision 32's store as the default and adds a trial destination. None reopens the per-role gate or the rule that a human approves.

**A1. The delivery mechanism is chosen per colony, and one of the two choices is a command.**

Decision 8 fixes the advertisement as name, description and the absolute path to the `SKILL.md`. That is right for the client-native bridge of Phase 4, where the client reads the file itself. It is the wrong shape when the colony wants to know what a run actually used: the path in the advertisement lets a role read the file behind the runtime's back, and the only evidence of that read is the client's transcript, which only some adapters can produce today.

So the advertisement gains a second form, and the colony chooses which one it uses:

| Mode | The advertisement carries | The body is obtained by | Usage evidence |
| --- | --- | --- | --- |
| `path` (default, decision 8) | name, description, absolute path | the role reads the file | the adapter's transcript, where it exists |
| `command` | name, description, and the command to run | `paseka skills load <name>` | the load record, on every adapter |

In `command` mode the path is not advertised, so the runtime is the only way to the body, and a load is a deterministic fact rather than an inference. The mode lives at `defaults.skills_delivery` (`path` or `command`; absent means `path`), is validated at load like `defaults.delivery`, is read from the frozen manifest, and appears in the resolved configuration view. A profile may override it for a model or adapter, and the selected profile is frozen with the trail. It is not a per-role setting: a colony that measures usage wants it everywhere, and a colony that wants a client to read skills natively wants `path`.

**A2. `load` joins the command group.**

Decision 26's group gains a tenth verb:

```
paseka skills load <reference> --trace <traceId> --agent <agentId>
```

It resolves the reference with the same resolver every other command uses (decision 27) against the configuration reference recorded for that run (decision 7), so a later configuration application or a store edit cannot make `load` disagree with what the run was offered. It refuses a reference the run's role does not carry — including a pattern, which names a set rather than one procedure — with exit 2 and `skill_not_offered`.

On success it prints the resolved location, then the body, then records the load:

```
path: <absolute path to the frozen SKILL.md>
dir:  <absolute path to the skill directory>

<body, verbatim, without frontmatter>
```

The directory is printed so a body that refers to `scripts/`, `references/`, or `assets/` can be followed: the files are reachable under `dir`, and the agent learns the location only by loading. That keeps `command` mode's property — the path is not advertised — while still making a supporting-file procedure usable. It appends `{name, contentHash, at}` to `.paseka/runs/<traceId>/<agentId>/skills-used.ndjson`, where `contentHash` is the SHA-256 of the served `SKILL.md` bytes (frontmatter included); it identifies the file as served and is distinct from the install-time provenance hash of decision 17. At finalize the runtime folds the file into the run's result as the deduplicated set of loaded skills; the first load of a name wins and repeats are ignored.

`load` is a read command with a side effect on the run's own record, so it speaks prose, not JSON. It exists because a colony that runs the same task twice and compares the two runs needs to know whether the procedure was even opened — a question the transcript cannot answer for every adapter. It works in either delivery mode: in `path` mode the agent can read the file directly, but a `load` it performs is still recorded, and the run's used set is the union of transcript attribution and load records, deduplicated by name.

**Resolving the colony.** The command is advertised as `paseka skills load …` by name, like `paseka event emit`; the colony does not promise an absolute binary path. It resolves the colony root in this order: `-C <dir>` when given, then `PASEKA_COLONY_ROOT`, then the nearest ancestor of the working directory that holds **both** `.paseka/colony.yaml` and the run directory `.paseka/runs/<traceId>/<agentId>/`. The run directory is part of the test because a git worktree carries the committed `.paseka/` but not the gitignored runs; walking up from `.paseka/worktrees/<traceId>/` therefore reaches the primary checkout instead of stopping at the worktree. When no candidate holds the run, the command exits 1 with an error that names the roots it tried, the trace and agent, and the `-C <colonyRoot>` that would fix it, so an agent that guessed wrong can retry.

**A3. A portable pack may carry skills.**

The out-of-scope item "Carrying skills in a portable Bee pack" is amended: a Nuc may carry skills alongside bees, prompts and cues, and `paseka nuc import` installs them into the store with `source: nuc` provenance.

The reason is the split the brief draws. A role's procedure, its prompts and its thresholds are one unit of content, and a colony that receives the procedure without the prompts that call it has received half of it. Keeping skills out of the pack made the pack unable to carry a methodology — and a methodology that cannot be moved between colonies is a colony's private improvisation, which is precisely what a portable pack exists to prevent.

The format change is additive: a pack without skills imports exactly as it does today.

**A4. The phase list gains the load path.**

Phase 1 becomes the store, its ledger, selection, the advertisement in both modes, the run record, `load`, and the reading half of the command group — `list`, `show`, `validate` — plus `remove`, `disable` and `enable`, which need nothing but the store itself. Phase 2 keeps usage attribution and the export section, and now sits beside the load record rather than ahead of it. Phase 3 also gains the trial destination of A5. Phase 4 is unchanged.

**A5. Approval can target a trail's configuration, for a trial.**

Decision 32's destination is the store. A Beekeeper also needs to try a proposed procedure on one trail before sharing it, and the trail already owns a pinned configuration that can change without touching the repository.

`approve <reference>... --into <trace> --role <role>...` builds one candidate configuration from the trail's active snapshot, adds the approved skill bundles, and adds each skill to the named roles' lists in that same candidate. It validates the whole candidate with the same skill rule set and with the configuration procedure validation, previews the diff, and applies once — a new configuration revision, never a mutation of an immutable snapshot. `--role` is required, because a trial that adds a skill no role carries changes nothing; the role-list change is part of the trial's diff and does not activate anything in the store (decision 16 still governs the store). When a role inherits the colony default, the trial writes the resolved default list plus the new skill, so the trial adds a procedure rather than replacing the inherited set. All skills in one invocation go to the same role set; a different mapping is a separate invocation.

The command refuses when the trail cannot activate immediately — a pending configuration change or an execution blocker — because a queued trial is not a result. `--dry-run` shows the same plan without writing anything.

A trial appends a `trialled` decision to the decision file of the trail that proposed the skill — each skill's decision goes to its own source trail — naming the destination trail, the roles, the content hash, and when. The proposal stays pending for the store: a trial is evidence, not an approval into the shared store. A later `approve` into the store writes `installed` and leaves the trial record in place. A refused proposal cannot be trialled.

Sequential trials are allowed: each apply builds its candidate from the then-active snapshot, so approving skill B after skill A yields a candidate containing both. They are not atomic across invocations, and a change that is still pending blocks the next — the configuration service refuses "another configuration change is pending". Several references in one invocation are therefore the recommended form: one candidate, one validation, one revision, all or nothing. The store destination follows the same batch rule: two sequential installs are safe, but a batch is what makes a partial approval impossible.

## Testing Decisions

Good tests here assert what an operator can observe: what a Bee was offered, what it was told, what a run recorded, and what a Beekeeper can approve. A test that reaches into the resolver's internals is testing the wrong thing.

- **Resolution** — a role with no list and no colony default receives nothing; a role with a list receives exactly that list; a role that declares a list replaces the colony default rather than extending it; an explicit empty list opts out; `*` expands to every valid, enabled skill, deduplicated and sorted by name; `paseka-*` selects the family; `*` on an empty store is allowed; another pattern that matches nothing fails the run; an invalid entry under `*` fails the run; a reference to a missing or invalid skill fails the run before the adapter starts; a limit breach fails the run; a disabled skill listed by a role is skipped and reported, not fatal. Nothing is silently dropped: a role either gets exactly its declared set minus the entries an operator explicitly disabled, or the run does not start.
- **Fail fast** — an invalid skill, a missing reference, a pattern that matches nothing, or a budget breach stops the run before the adapter starts and fails `doctor`; a role offered 33 skills or a skill file over 256 KiB fails the run before the adapter starts; a store over 8 MiB fails `doctor` and `validate`; a candidate configuration containing an invalid skill is refused; an invalid skill that no role references is a `doctor` and `validate` error but does not block an unrelated run.
- **Configuration** — `skills` is tri-state: absent inherits `defaults.skills`, an empty list opts out, a non-empty list replaces; the loader distinguishes absent from empty; a profile may override the default list, a role's list, and `skills_delivery`, and the effective values are frozen in the trail; `skills` in `<role>.local.yaml` is a load error; `defaults.skills_delivery` accepts `path` and `command`, absent means `path`, and anything else fails the load.
- **Pinned configuration** — a run keeps the skill set the trail froze even after `.paseka/skills/` changes; an edit to the store after trail start reaches a trail only through an explicit configuration application, never through the next dispatch; a missing, corrupt, or invalid snapshot blocks the run instead of falling back to the live store; `list` and `show` still describe the repository store, and `load` resolves the run's frozen copy.
- **Namespace** — a bare name resolves to the store; a tier-prefixed (`shared:`, `local:`) or path-shaped reference is reported as an invalid reference and never resolved; a reference that matches no skill is reported by name. There is no precedence between roots to test, because there is one root.
- **Validation** — a skill whose directory name differs from its metadata name is rejected; a name with an uppercase letter, a leading hyphen, a doubled hyphen, or excessive length is rejected; a missing or empty description is rejected; a valid skill of the same shape is accepted. The same rules must produce the same verdict on scan, on approval, at dispatch, and in `doctor`.
- **Delivery** — the rendered advertisement is a section appended after the rendered system template and is not part of any template file; it contains each resolved skill's name and description plus, per the selected mode, either its frozen location or the load command, and no skill body; a bee with no system template gets the section as its whole system prompt; in `path` mode the advertised location is inside the trail's frozen configuration, not the live store; the advertisement is written into the run's system-prompt file; a run with no skills produces no advertisement; the advertisement is identical regardless of which adapter consumes it.
- **Delivery modes** — in `path` mode the section carries the frozen `SKILL.md` path; in `command` mode it carries the `paseka skills load` command and no path; a script Bee still receives absolute locations in its environment in both modes; the mode is read from the frozen manifest, a profile override is frozen with the trail, and a configuration apply changes it for later runs only.
- **Run record** — an AFK run and an interactive session each name the skills that were offered in their request record; the names survive a later change to the role's configuration.
- **Interactive and resume** — an interactive session receives the same advertisement as an AFK run; resuming a session neither re-injects the section nor changes the offered set; a configuration application during a session changes neither.
- **Usage attribution** — a transcript containing a read of a skill file attributes that skill; a transcript containing no reference to a skill attributes none; a command-mode run attributes a skill from its load record; a path-mode run attributes from its transcript, from a load record, or from both, and the used set is the union deduplicated by name; a run whose adapter has no usage capability and whose skills were never loaded records an explicit "not available" reason rather than an empty result; usage attributed for one run does not leak into another.
- **Proposal** — the Archivist's skill intent writes a bundle into the comb and publishes an `INSIGHT/skill.proposed` discovery; the note intent still writes its report and publishes its note; the runtime writes no decision while the proposal is pending; the role's completion contract demands the note for the note intent and the proposal for the skill intent; a run that publishes neither fails its contract.
- **Approval** — approving a valid proposal installs it into the store and records provenance; approving a proposal whose metadata is invalid installs nothing; approving over an existing skill is refused without an explicit override; several references in one invocation are all-or-nothing, so one invalid or conflicting skill writes none; no path exists by which a proposal installs itself.
- **Trial** — `approve --into <trace> --role <role>` adds the skill and the role reference in one candidate, applies one new revision, and leaves the store unchanged; a role that inherits the colony default receives the resolved default list plus the new skill; the command refuses without `--role`, while a change is pending, and while an execution blocker holds activation; a trial appends a `trialled` decision and the proposal stays pending for the store; a later store approval writes `installed` and the trial record remains; two sequential trials work when the first is applied, the second is refused while the first is pending, and a batch of two references produces one candidate containing both.
- **Trail decisions** — a pending proposal is found from its discovery event; installed, refused, and trialled come from the decision file; a missing bundle is reported; purging the trail removes the proposal and its decisions; a decision on one machine is not visible on another because run data is not shared.
- **Removal and neutralisation** — removing a skill reports the roles that reference it and refuses without an explicit override; removing a skill does not delete the trail decisions about it; a disabled skill is not offered but remains in the store and the ledger.
- **Isolation** — trail cleanup, worktree cleanup, and cache purging leave the store untouched; the store is never written by a Bee run.
- **Script adapter** — a script Bee receives the skill manifest in its environment, with absolute paths, and a script that ignores it is unaffected.
- **Load** — `load` prints the frozen `SKILL.md` path, the skill directory, and the body without frontmatter; the printed directory resolves a `scripts/` reference; it refuses a reference the run was not offered, including a pattern, with exit 2 and `skill_not_offered`; it appends one record per load and the finalize result is deduplicated by name with the first load winning; it resolves the colony from `-C`, then `PASEKA_COLONY_ROOT`, then the nearest ancestor holding both the colony and the run directory, so a worktree run is served by the primary checkout; with no candidate it exits 1 and names the roots tried, the trace and agent, and the `-C` that fixes it.
- **Command surface** — the group invoked bare prints help and changes nothing; the listing reports the state and the roles for each skill, with a pattern-named role shown for every skill it resolves to; a mutating command refuses a pattern while `validate` accepts one; a dry run of `approve`, `reject`, or `remove` leaves the store byte-identical and prints the plan; `disable` and `enable` name the affected roles as they run and are reversed by each other; an ambiguous approval without a trail names the candidates instead of choosing; several references are approved in one batch and none is written if one fails; the read commands emit a parseable machine contract on request and the mutating commands do not depend on one; a reference that the runtime would not resolve is refused by the command that would act on it.

Prior art in-repo: the colony configuration load and validation tests, the trail-configuration capture, stability, and missing-content tests, the run-directory and run-record tests, the launch resolution tests for the merge and environment layers, the adapter capability tests for the session-log resolver, the runtime dispatch tests over rendered prompts, the artifact comb tests including the path-escape cases, the export include tests, the completion-contract tests, the command-level tests for the cue and task listings and their table output, and the dry-run and force-flag tests on the nuc import.

## Out of Scope

- A team-shared proposal decision log, or sharing proposal decisions through git. Decisions live in the trail's run data, are machine-local, and are deleted with the trail.
- Applying one approval to several trails at once. A trial names one destination trail per invocation.
- Writing skills into client-specific discovery directories, or configuring a client to point at a skills directory. This is the native bridge, a later phase of this spec.
- Remote skill catalogs, HTTP-sourced skills, or any skill distribution mechanism beyond the store.
- A machine-local skill root, a `skills` key in the bee's local overlay, or a tier prefix that selects one. A profile may select among committed procedures (decision 3), but it cannot supply one, and the store is committed configuration: a procedure whose availability depends on the host is not reproducible in a trail.
- Automatic approval of a proposal, under any policy, flag, or colony setting.
- A skill marketplace, a skill registry across colonies, or publishing a skill to a team catalog.
- A graphical skill editor, or any console surface that writes a skill's body.
- Editing a skill's body in place from the console. The store is plain files and the Beekeeper's editor is the editor.
- Enforcing that a Bee followed a skill. The layer records what was offered and what was reached for; it does not police compliance.
- Accounting for the token cost of a skill separately from the run's usage, or per-skill cost reporting.
- Semantic versioning of skills, or a dependency or compatibility model between skills.
- Skills that reference other skills, or any transitive resolution.
- Per-task or per-sector skill selection. Selection is per role.
- A per-role delivery mode. The mode is colony-wide and a profile may override it.
- A pattern dialect beyond `*`: no `?`, character classes, alternation, or regular expressions.
- Skill selection by the task's intent, by the task's text, or by any automatic matching. The gate is declared, not inferred.
- Changing what a role's prompt templates contain, or introducing prompt composition that includes a skill body.
- Changing how the existing note-producing intent of the Archivist works.
- Carrying skills in a portable Bee pack. The pack format is unchanged by this spec. **Amended by A3**: a pack may carry skills, and `paseka nuc import` installs them.
- Reading a client's own skill configuration to discover what the client would have offered on its own.
- Fetching a skill from a URL, from another colony, or from a catalog. The store is filled by hand or by approval, and nothing is downloaded.
- An interactive full-screen browser for the store. The listing is a table and the store is a directory; a browsing UI is the console's job, in a later phase.
- A command that writes a commit. A store change that must be shared is a change the Beekeeper commits.
- Renaming a skill. A rename is a new skill and a removed one, because a name is an identity that other files and roles refer to.

## Further Notes

- **Phasing.** Phase 1 is the store, its ledger, selection, the advertisement in both modes, the run record, `load`, and the reading half of the command group — `list`, `show`, `validate` — plus `remove`, `disable`, and `enable`, which need nothing but the store itself. It is the implementable core and needs no new event kind. Phase 2 is usage attribution and the export section. Phase 3 is the proposal and the decisions on it — `proposals`, `approve` (store and trial), `reject` — with the console surface; its decisions live in the trail's decision file while the store ledger keeps only the enabled/disabled state. Phase 4 is the native client bridge. The phases are ordered so that each is useful alone: a colony with Phase 1 can give a Bee a procedure, know it was offered, and manage the store from the shell; Phases 2 and 3 add the measurement and the origination; Phase 4 improves the ergonomics for clients that have them.
- **The path is printed on demand, not advertised.** `command` mode keeps the path out of the advertisement so a load is a recorded fact, but a procedure that bundles `scripts/` or `references/` cannot be used without knowing where it lives. Printing the resolved directory in `load`'s own output is the narrow answer: an agent learns the location only by loading, the load is already recorded, and the files under that directory are read the same way any other file the procedure names is read.
- **Three logical blocks, two files.** The role's instructions, the skills section, and the task prompt are three logical blocks. No client accepts a third system channel, so the first two share the run's system-prompt file and the task stays in `prompt.txt`; the split is what makes the block auditable and independent of any template, and it keeps Cursor's single positional prompt and Pi/Claude's system file on the same shape.
- **The advertisement block is the compatibility surface.** Clients advertise skills to a model as a name-and-description block, and Paseka now produces the same shape. In `path` mode, a Bee reading a Paseka-advertised skill is reading a file the client would also have read, at a path the client would also have accepted; in `command` mode it gets the same content through `load`. Either way the two mechanisms do not conflict when the native bridge lands — a skill advertised twice is idempotent from the Bee's point of view, and a skill offered natively is one the runtime also counted.
- **Provenance in the skill's own metadata.** The standard's metadata field is a string-to-string map, which is exactly enough for a source, a trail identifier, a role name, an approval timestamp, and a content hash. Keeping provenance inside the skill rather than in a committed index means it travels with the file — including into another client's directory, and into another colony — which is the property that makes an approved skill explainable rather than mysterious. The committed ledger holds only the enabled/disabled state, so there is no second provenance to reconcile.
- **Proposal decisions live with the trail, not with the store.** A proposal is a trail's output, and so is the decision about it. Keeping both in the trail's run data means no merge conflicts in a committed decision log, no cross-machine state to reconcile, and a proposal that disappears with the trail that motivated it. The price is that a decision is machine-local: a colleague on another clone sees the proposal as pending until the installed skill is committed, and a refusal is not shared through git. That is the right trade while a proposal is per-trail evidence; a shared decision log is a different feature.
- **The native bridge's open question.** Every client that supports skills reads a directory of them, and OpenCode accepts an explicit list of directories in its configuration, so the bridge is technically small. What is not settled is where a bridged directory lives for a role that works in the repository root rather than in a worktree: a directory of links placed there would appear in the Beekeeper's working tree, and a colony that cannot answer "where do the links go, and who removes them" should not ship the bridge. In a worktree the answer is already obvious, and the bridge can start there.
- **Attribution is a measurement, not a proof.** A use recorded from a transcript is evidence that a skill's file was read, not evidence that its instructions were followed. The export therefore reports what was reached for, and the wording of that report should not drift toward claiming compliance.
- **Fail fast, never degrade.** The skill set is a declared gate, so a role that receives a different set than its configuration declares has silently changed behaviour. A missing reference, an invalid skill, a pattern that matches nothing, or a budget breach therefore stops the run before the adapter starts; a candidate configuration with any of these is refused outright, because an experiment that runs with the wrong procedure measures the wrong thing. `doctor` reports the same verdict as an error. Dropping the offending entry and continuing is the one outcome the layer must not produce.
- **Resolution is pinned to the trail, not to the checkout.** A skill edit is a configuration change, and spec 042 already decides how a trail adopts one: an explicit application at a safe boundary. A resolver that read the live store would make an edit change the next run silently and make two runs in one trail incomparable, which is the failure this layer is supposed to remove.
- **The store is deliberately not a client directory.** It is tempting to make the store the same directory the clients already read — `.agents/skills/`, for instance — so that no delivery work is needed at all. That would trade away the per-role gate, the run record, and the attribution, all of which are the reason this spec exists; a client that advertises every skill it finds to every agent it starts cannot express "this procedure belongs to the release role only". The trail configuration may freeze a client directory as configuration input, which is capture for reproducibility, not a gate.
- **A skill is content that a Bee wrote about how to work.** The whole layer is only safe because of the separation in decision 16: the store holds procedures, the role configuration decides who uses them, and the Beekeeper approves both halves separately. A future feature that collapses those two in the shared store — a proposal that edits a role's list, an approval that activates for every role — should be read as an escalation and rejected. A trial (A5) is not that: it writes one trail's pinned configuration, is visible in that trail's diff, and is reversed by applying the previous snapshot.
- **The command group is the layer's only human surface in the shell.** Ten verbs, one namespace, one reference syntax. The design pressure that shaped it is that five of the ten change a reviewed artifact; the three destructive or terminal ones — `approve`, `reject`, `remove` — preview their plan, refuse on a conflict, and name their repository consequence, while `disable` and `enable` are reversible flips that report their blast radius as they run. A store command that reported success without saying "the working tree now has one untracked file" would leave the Beekeeper believing the team has a procedure the team does not have.
- **The wildcard is a gate, not a default.** `*` is an explicit opt-in to the whole store: adding a skill changes every `*` role on the next trail, a 33rd skill breaches the per-role budget, and one invalid entry blocks every `*` role. That is the trade for not maintaining a list; the store diff is where the change is reviewed, and `doctor` must be clean before a `*` role runs.
- **The listing's roles column is the reason the listing exists.** A store is easy to list; what a Beekeeper cannot answer by looking is which roles actually carry a procedure, and therefore whether removing one is safe. That answer is computed from the role configurations rather than remembered, and it is the first thing the table shows after the name. A pattern or `*` is resolved for this question, so a wildcard role appears against every skill it actually receives.
- **Refusal is a recorded state, not an absence.** A refusal is a line in the trail's decision file; a disable is a line in the store's state file. Neither is an absence, and neither lives in the other's file. A proposal that was looked at and turned down is a decision, and a proposal nobody looked at is not the same thing.

## Implementation Plan

The plan is a map, not a second specification: each phase lists what ships, the seam it touches, and the use cases and testing decisions that accept it. Decisions and wording live above.

**Phase 0 — foundation (the first slice of spec Phase 1).** Store path, scan, reference and pattern parsing, validation, and the enabled/disabled state file in a new `internal/skills`; the presence-aware `skills` field, `defaults.skills`, and `defaults.skills_delivery` in `internal/colony`; the profile schema (`skills`, `skills_delivery`) under spec 027; the local-overlay rejection. Trail configuration captures the ledger and a home profile's `config.yaml` (spec 042). Ships the core, a first `paseka skills list` and `validate` against the live store, and the `doctor` findings.

Accepts: user stories 3, 4, 10–13, 42, 57–63; Testing Decisions **Configuration** and **Validation**.

**Phase 1 — resolution, delivery, record, `load`.** One resolver pinned to the trail snapshot; the advertisement section rendered where both the dispatcher and the session manager already render a system prompt; skill references on the launch request; the script environment manifest; `skills []string` in `protocol.Request` written by both call sites; `load`; and the rest of the store command group (`show`, `remove`, `disable`, `enable`). Fail-fast and the fixed budgets are enforced here.

Accepts: user stories 1–20, 32–38, 41–47, 54–63, 69–71; Testing Decisions **Resolution**, **Fail fast**, **Configuration**, **Pinned configuration**, **Validation**, **Delivery**, **Delivery modes**, **Run record**, **Interactive and resume**, **Load**, **Command surface**.

**Phase 2 — attribution and export.** The transcript pass reuses `adapters.ProjectToolCalls`; the used set is the union of transcript evidence and load records; the export section reads the offered set, the use evidence, and the bodies from the frozen copy.

Accepts: user stories 17–20, 36–37, 47; Testing Decisions **Usage attribution**.

**Phase 3 — proposals, approval, trial.** `INSIGHT/skill.proposed`, the Archivist skill intent and per-intent contract, the trail-scoped `skill-proposals/decisions.ndjson`, `proposals`, batched `approve` into the store or `--into` a trail candidate, `reject`, and the console surface. The store install uses the shared validator; the trial is one configuration revision and one candidate.

Accepts: user stories 21–31, 64–68; Testing Decisions **Proposal**, **Approval**, **Trial**, **Trail decisions**; amendments A3 and A5.

**Phase 4 — native bridge.** Deferred; decision 24 is the whole design and its link-location question is the only open item.

**Cross-spec dependencies.** Spec 042 must capture the ledger and a home profile's `config.yaml`, and its candidate validation must call the shared skill validator. Spec 027's profile schema gains `skills` and `skills_delivery`. The artifact and proposal-patch patterns of specs 014 and 039 are reused, not extended.
