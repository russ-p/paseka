# Spec 035: Queen Console Redesign

## Status

**Draft**
Initial design spec for migrating Queen Console to Svelte 5 + Tailwind v4 + DaisyUI with new layout, routing, and theming. Delivery is phased: the preview foundation, the application shell, and every route have landed, so nothing resolves to `PagePlaceholder` any more. Worktrees is the first route whose scope was decided rather than ported — the worktree table and the orphan prune left the Git page for it — Bees is the second and the first to need the server to answer a second question, and Settings is the third and closed the group. It is also the one place the console is read-only about the colony's own configuration, which is a scope decision rather than an unfinished route: writing config is a platform capability, tracked in [Backlog](../plans/backlog.md), and not something this migration owes.

## Problem Statement

The current Queen Console uses an older frontend stack that limits developer experience, theming flexibility, and component composability. Operators need a modern, responsive interface with:
- Consistent theming (light/dark/custom) via DaisyUI, including Catppuccin Latte, Frappé, Macchiato, Mocha
- Clear navigation with left-side slide-out menu and top status panel
- Dedicated routes for Dashboard, Traces, Bees, Worktrees, and Settings
- Better TypeScript integration and component reuse
- Faster builds and hot-module replacement during development

## Solution

Rebuild Queen Console as a Svelte 5 application using Tailwind v4 and DaisyUI for styling. Adopt file-based routing with explicit routes and implement a persistent shell layout: top panel with cluster/NATS status indicators, left slide-out menu replacing current tabs, and a main content area per route. Extract shared UI components (cards, tables, forms, status badges) into a component library. Configure DaisyUI themes and expose a theme selector in Settings. During migration, the redesigned console is published as a preview under `/next/` while the legacy console remains the default at `/`; the root route is not redirected or replaced until feature parity and cutover approval.

## User Stories

1. As a Beekeeper, I want to switch between light, dark, and custom DaisyUI themes, so that the console matches my environment and accessibility needs.
2. As a Beekeeper, I want a top panel that always shows the NATS connection state, the hive runtime with its Start/Stop control, live bees, host, and git, so that I can assess system state at a glance without the legacy console. NATS reads as a transport icon beside the colony identity rather than a worded badge; the active trace count lives on the Dashboard.
3. As a Beekeeper, I want a left-side navigation menu with icons and labels for Dashboard, Traces, Bees, Worktrees, Settings, so that I can switch contexts without losing scroll position.
4. As a Beekeeper, I want a dedicated Dashboard route (`/next/dashboard`) showing colony overview, recent signals, and quick actions, so that I land on a useful summary when I open the redesigned console.
5. As a Beekeeper, I want a Traces route (`/next/traces`) with a filterable, paginated list of trails, so that I can scan execution history efficiently.
6. As a Beekeeper, I want a trail's detail on its own route (`/next/traces/:id`) with a shareable link, so that I can send a colleague straight to the trail I am looking at.
7. As a Beekeeper, I want a Bees route (`/next/bees`) listing all registered bees with status, last run, and adapter info, so that I can monitor bee health.
8. As a Beekeeper, I want a Worktrees route (`/next/worktrees`) showing active worktrees, their branches, and associated traces, so that I can manage isolation contexts.
9. As a Beekeeper, I want a Settings route (`/next/settings`) to configure themes, NATS endpoints, API keys, and notification preferences, so that I can customize the console without editing files.
10. As a Beekeeper, I want the console to persist my last active route and theme in localStorage, so that my preferences survive reloads.
11. As a Beekeeper, I want keyboard shortcuts (e.g., `g d` for Dashboard, `g t` for Traces) to jump between routes, so that I can navigate quickly.
12. As a Beekeeper, I want the console to gracefully degrade when NATS disconnects, showing a reconnecting banner and queuing mutations locally, so that I don't lose work during transient outages.
13. As a Beekeeper, I want the redesigned console preview to be served from the same Go binary via `paseka console` at `/next/`, so that deployment stays a single binary while I compare it with the legacy console.
14. As a developer, I want TypeScript types generated from the Go event contracts (SIGNAL, INSIGHT, MUTATION, VERIFICATION), so that frontend consumes typed payloads.
15. As a developer, I want a component storybook or visual regression setup, so that UI changes are reviewed consistently.
16. As a Beekeeper, I want the console to be responsive down to 768px width, collapsing the left menu into a bottom sheet on mobile, so that I can check status on a phone.
17. As a Beekeeper, I want forms (new task, new bee, new worktree, settings edits) to open in a modal or drawer triggered by a button, not consume a full column, so that I keep context of the list view while creating or editing.
18. As a Beekeeper, I want the legacy console to remain available at `/` throughout migration, so that unfinished redesign work cannot block current operator workflows.

## Current Section Design Audit

Each current tab audited for the redesign: what it does, which components it relies on, and a design proposal (keep as is / collapse under a button / move elsewhere).

### Dashboard

- **Functionality:** Colony-wide snapshot. Stat grid (NATS status, active sessions, active worktrees, task counts by status), recent traces, failed runs, recent insights. Quick actions: "Run cue" (opens cue modal) and "Refresh". Header panels show Hive runtime (Start/Stop), Live bees, Host, Git.
- **Components:** `stat-grid` tiles; compact lists (recent traces / failed runs / recent insights); cue modal (mnemonic picker + text form); header runtime/agents/host/git panels; toast container.
- **Design proposal:** Keep as the redesigned landing page. Collapse "Run cue" into a header quick-action button; drop the manual "Refresh" in favor of polling and the existing console event stream. Keep stat grid + recent traces front and center; move failed runs and recent insights down or push them to Traces/Timeline routes. The four header panels (Hive runtime with Start/Stop, Live bees, Host, Git) are promoted to the shared top panel rather than staying Dashboard-only, so the runtime control is reachable from every route.
- **Implemented:** `/next/dashboard` composes the shell with a five-column stat grid: `StatTile` for active traces, active sessions, and active worktrees, plus a task-counts tile on `lg:col-span-2` that badges the count in the status tone and leaves the status word as quiet text. Recent traces are a `TraceRow` list, failed runs a `DataTable`, recent insights `SignalCard`s. The four header panels moved to the topbar, so the grid repeats none of them — not the runtime, not the bees, and not NATS, which the topbar already shows as a transport icon beside the colony identity. The grid reads from the single dashboard poll in `consoleStatusStore` rather than polling `/api/dashboard` a second time, and `store.refresh()` replaces the dropped Refresh button after a cue is published. Failed runs are filtered to `failed`/`cancelled`/`killed` on arrival, since the projection also carries finished runs the legacy console happened not to render. Trace rows carry no `href` until `/next/traces/:id` exists, so a row shows state but does not promise a destination.

### Traces

- **Functionality:** Scrollable trail list and a detail panel: meta (ID, title, status, standing), energy budget bar with top-up buttons (+1/+5/+12), LLM usage, worktree block, trail artifacts with inline preview, tasks, runs, recent events. "Open timeline" jumps to Timeline pre-filtered by the trace.
- **Components:** `session-list` rows (`TraceRow`), detail panel with collapsible `trace-section` blocks, artifact preview area, `compact-meta` definition lists, energy bar controls.
- **Design proposal:** Keep — this is the core inspection surface. Split it: `/next/traces` is a `DataTable` over `GET /api/traces`, and the detail collapses into its own route `/next/traces/:id` rather than a drawer (user stories #5 and #6), so a trail is linkable and the browser back button means something. The artifact preview leaves the page flow entirely and opens in a `Modal`, because a comb file body is a read-once detour, not a column.
- **Implemented:** The list is a `DataTable` (Trace, State, Runs, Tasks, Bees, Last activity) with a client filter and no page of its own — `pageSize={0}`, so every trail the store holds is on screen and no `?page=` is written. `tracesStore` pulls 50 at a time by cursor, asking for 51 and dropping the probe row so "is there more" is answered rather than guessed, and offers "Load older trails" while the server has more. The State column is empty unless a trail is active or has failed, so the eye catches the rows that matter instead of reading `4 runs` twice. The detail route is `TraceDetail.svelte` behind a one-line `+page.svelte` that reads `page.params`, with sections in priority order — Trail on two thirds of a desktop row beside the Honey reserve, then Trail artifacts, Tasks, Runs, and Worktree / LLM usage / Recent events collapsed. The trail id carries a copy-to-clipboard button, since it is the value an operator pastes into a CLI. `View` on a comb file opens `ArtifactViewModal`, which fetches the body on demand and renders server markdown as HTML or anything else in a `<pre>`. A top-up patches the reserve from the response and reports through a `Toast`; the comb failing is reported apart from the trail, since one endpoint failing must not hide the other. Task and run rows stay inert while `/next/tasks` and `/next/runs` are placeholders.

### Timeline

- **Functionality:** Event feed of the four contracts (SIGNAL, INSIGHT, MUTATION, VERIFICATION) with filters (trace, task, bee, type, kind, severity), raw-JSON toggle, and "Load more" pagination.
- **Components:** filter bar form, feed list, raw toggle checkbox, "Load more" button.
- **Design proposal:** Keep, but collapse the filter bar under a "Filters" button to recover vertical space. Replace the raw-JSON checkbox with a per-event expand action. Consider chunked/streamed loading instead of "Load more".
- **Implemented:** `/next/timeline` takes the first two proposals and defers the third. The filter bar is a folded `Section` whose `open` is simply `applied > 0`: arrive with nothing applied and the feed owns the screen, arrive from a trail's *Open timeline* and the panel is open, because that operator must see the scope they were sent with and be able to drop it. The collapsed summary line names the active filters, so a narrowed feed never looks colony-wide. The raw-JSON checkbox is gone: the raw `protocol.Event` already ships on every row, so each row carries a borderless *Raw event* disclosure — the legacy's checkbox put a `<pre>` inside every card at once, and a modal would mean opening and closing one per event. **Chunked or streamed loading is deferred, and so is a poll.** The feed is cursor-paginated history; a timer that prepends to a list an operator is scrolling, or silently replaces the page they scrolled to, is worse than a Refresh button, and one read is in flight at a time because a second Apply against one cursor could repeat or skip the boundary event. A failed load-more keeps its cursor so the button is a retry, not a dead end. The trail detail's *Open timeline* is now a real deep link (`/next/timeline?trace=<id>`) rather than a tab switch with the filter set in memory, and it seeds the form and the first read together so the scoped feed is never briefly the colony's. On a colony-wide feed the row's trace id links to the trail while the summary stays plain prose — a feed of underlined headlines reads as a wall of links — and a feed already scoped to one trail drops both. `SignalCard` took two optional props for this (`expand`, `traceHref`), so the Dashboard, the trail detail, and the feed stay one component.

### Tasks

- **Functionality:** Task creation (title, body, bee, trace ID, sector, intent, review policy, dependencies, autorun), a column-based task board, task detail (meta, description, linked runs), and approve/reject review actions (approval summary, merge commit message, PR title/body/draft/hooks).
- **Components:** full-column create form, `task-board` kanban columns, task detail panel, review action forms (approve + reject).
- **Design proposal:** This is the only tab with a full-column form — move creation into a Modal toggle on the board (user story #16) and reclaim the column for the board. Promote the board to a real kanban (columns per status). Collapse approve/PR fields under the Approve action; keep Reject minimal.
- **Implemented:** `/next/tasks` and `/next/tasks/:traceId/:taskId`. The form moved into a **`Drawer`** — a button on the board, so the full column is reclaimed, and the create panel is `Modal` with `placement="right"` rather than a second focus implementation, which is what the audit asked for and what `Drawer` had been promised as since the shell landed. The board is a **real kanban**, one column per status, and it **wraps** rather than scrolling sideways: seven statuses in a row would put the last two off a laptop's edge and out of reach on a phone. It keeps the server's group order, because that order is the pipeline. **Each column scrolls inside its own bounded box**, which the fixtures could not have told us — this colony holds 29 completed tasks beside one ready one, and an unbounded column buries the work at the top of a three-thousand-pixel ribbon; the header count stays visible so a scrolling column still says how much it holds. Creation sends **only the fields the operator filled**: a present-but-empty trace id is not the same as an absent one, where absent means "generate one", and the intents in the bee's dropdown come from `GET /api/bees` so a bee that adds a prompt template needs no console change. Approve and reject **stay on the task page** rather than moving to the review queue, because that is where a task is read and a gated task that could not be answered from the page it is read on would be a regression against the legacy console; the PR fields are collapsed under Approve and shown only when the task delivers as a pull request, and Reject stays one box whose feedback becomes the rework task's body. Two decisions the real data forced, both now covered by tests: **a card is keyed by trail *and* task id**, because `_review` is the default id for a rework task and five trails each have one, and keying on the task id alone threw `each_key_duplicate` and rendered an empty page; and **the status badge reads the polled board row rather than the once-read detail**, so a task approved in another tab stops claiming it is waiting for review within one poll instead of disagreeing with the board it links back to. Writing the shared `ReviewActions` for Reviews also corrected two things here: the decision is offered behind **both** review flags, because the shared component renders Approve and Reject together and a task the ledger lets you approve but not reject would otherwise get a button the server refuses — which is also what the legacy required; and the flags **fall back to the fetched task detail** when there is no board row at all, because a task deep-linked from a trail or a run is not on the board and failing closed there left a gated task with no way to be approved from the page it is read on.

### Reviews

- **Functionality:** Review queue (tasks in `waiting_review`), proposal detail with summary, merge diff preview (stat + file list + diff2html viewer), inline review comments with drafts, approve/reject with PR creation and final merge gate; separate full-screen "Merge preview" layout.
- **Components:** queue list, proposal detail panel, merge-diff section, full-screen merge preview (file filter, file list, side-by-side/unified viewer, comments panel), review action forms.
- **Design proposal:** Keep — the merge preview + comments panel is the most complex but most important surface. Keep the full-screen diff as its own route. Rebuild on dedicated `DiffViewer` / `CommentThreads` components; gate show/hide of PR fields behind the delivery type (merge vs PR).
- **Implemented:** `/next/reviews`, `/next/reviews/:traceId/:taskId`, and `/next/reviews/:traceId/:taskId/preview`, on dedicated `DiffViewer` and `CommentThreads` components, with the PR fields gated behind the delivery type exactly as proposed. The full-screen diff **is its own route** rather than the legacy's trick of hiding one `<main>` and showing another under a single URL, so a preview can be linked to and the browser's Back agrees with what is on screen. Four decisions the real console forced, all now tests: **the diff is parsed by this console instead of by diff2html**, because the legacy handed diff2html its patch and then scraped the generated DOM (`td.d2h-ins .line-num2`) for the line numbers a review comment anchors to — coupling comment anchors to a third party's private markup, so a diff2html upgrade would have been a review-page change; `lib/diff.ts` parses a patch into rows carrying their own line numbers, which also keeps the body as Svelte text nodes rather than a library's `innerHTML` and leaves cytoscape the console's only third-party styling exception. The parser also **trusts each hunk header's own line counts**, which is what stopped every file from rendering a phantom numbered row past its end — a patch ends in a newline, and read as context that newline became a line one past the file. **A moved `headSha` holds the comment packet rather than voiding it**: the drafts are kept, the send is disabled, and the panel names both commits, because a note's line numbers mean nothing against a different commit but the thinking behind them is still the reviewer's. Holding the send also required **a same-trail re-read to leave the diff on screen** — the comments panel is mounted beside it, so blanking the patch to show a skeleton would unmount the panel and eat the drafts, which is precisely the loss the warning exists to prevent. And the file list **wraps** paths instead of truncating them: `config.go` and `config_test.go` both truncated to `internal/gate/telegram/con…` on the real diff, which is the one thing a diff file list must not do. PR fields are keyed on `pull_request`; an earlier version compared against `pr`, which no delivery equals, so they silently never appeared on a colony that publishes them — and writing the shared `ReviewActions` for this page surfaced it on the task page too.

**Unified and split both ship,** from that one parser: the split view pairs each run of removals with the additions that replaced them and leaves a filler where one side runs out, so the two layouts cannot disagree about a line number — and split is the only way to anchor a note to the *old* line of an unchanged line, which is usually why the note exists.

### Sessions

- **Functionality:** Launch interactive HITL sessions (bee, task body, optional raw prompt override, trace ID, intent), pending invites, session list, session detail with an xterm terminal (PTY via WebSocket), resume/stop, and a transcript.
- **Components:** launch form, invite list, session list, detail panel, xterm terminal with Widen toggle, transcript `<pre>`.
- **Design proposal:** Keep. Terminal interaction is space-hungry — promote "Widen" to a proper full-screen focus mode. Move the launch form into a Drawer (user story #16) and hide the resume field until a prior session is selected. Group invitations under a collapsible "Pending invites" header.
- **Implemented:** `/next/sessions` and `/next/sessions/:sessionId`, the last legacy surface. The three proposals are all in, and each turned out to be a different answer than the legacy's shape. **The full-screen terminal is a mode, not a route** — the legacy's Widen button collapsed the page to one column and *hid the launch form and the whole session list*, with that same button as the only way back, so a live session was one click from unreachable; here the terminal's box changes and nothing else does, the URL still names the session, and Escape leaves. **The launch form is a `Drawer`** as proposed, and it is the second user of one, which is the evidence that the primitive was the right extraction. **Invitations are a collapsible header**, open when there are any, because a colony with no pending invite spends most of its time in the empty state and should not spend a screen on it.

**A session has an id, so a session is a link.** The legacy made each row a `<li>` with a click handler — no `href`, no `tabindex`, no role — so a session could not be selected with a keyboard at all and could not be linked to or deep-linked. Rows are real links into a detail route, and a session older than the recent window is fetched on its own rather than rendering blank.

**The terminal reconnected several times a second, and it was two loops, not one.** A store that polls replaces its selected session with a fresh projection on every tick, and anything `$derived` from it is invalidated with it — so an effect that opened the PTY socket re-ran on every poll, and because it returned a `close` cleanup, each re-run tore the relay down and opened another one: ~180 sockets and ~180 list reads per five seconds, with the previous sockets left open and the "relay closed" notice flashing each time. Two things fix it, and both are about ownership rather than timing. **The connecting effect is idempotent and returns no cleanup**: it decides what should be connected now and does nothing when it already is, tearing down only where a change is observed — a different session, a detach, unmount. And **`start()` reads no reactive state**, because a page calls it from inside an effect and anything read there becomes a dependency of that effect; it had been reading the selected session to pick a timer period, which the list poll then wrote back, so every poll restarted the polling that issued it. Measured on a live `opencode` session: one socket, one 48 KB scrollback frame, no alerts, and 2 list reads and 6 detail reads over twelve seconds.

**A bee's `intents` is `null`, and two forms had the same crash waiting.** `console.BeeView.Intents` carries no `omitempty`, so the nil slice `prompts.DiscoverIntents` returns for a bee with no prompt templates is marshalled as `null` — four of the seven bees in this colony. The task create form and the session launch form each read `bee.intents.includes(...)` and `bee.intents.length` inline, which is how picking an ordinary bee in the Sessions drawer took the page down, and how the identical expression came to be sitting in the Tasks one. `beeIntents` is now the single reader; the topology label is untouched because `colony.Bee.Intents` *does* carry `omitempty` and is genuinely absent rather than null, and a bee with no intents is a narrower form rather than a dead end — the launch button waits only for a prompt.

**Six things the legacy fetched and then threw away are now on the page,** each because it answered a question an operator would otherwise have to ask elsewhere: the **adapter**, which decides whether a session can be resumed at all; the **duration**, which the console already computed for Runs and Traces and never used here; the **provider session id**, which is what a resume continues; the **state as a word rather than a class**, where `cancelled` reads as **stopped** — the legacy badged it with the `failed` class, so stopping a session and watching one crash were the same red badge; the **relay's refusal, translated**; and the row's **adapter next to the bee**, because this colony has three `main-guard` sessions in a row and a row showing only the bee is three identical-looking rows.

**Stop asks, and then says which stop it was.** A local stop is `Process.Kill` and a cross-process one is `SIGTERM` — the legacy offered that as one click with no confirmation and discarded the `{status}` body, so a hard kill and a polite request looked identical. It now confirms, and reports the difference: *killed, with no chance to clean up* against *asked to exit, and can finish what it was doing*.

**A relay refusal is a diagnosis, not a dead terminal.** The console can only relay a PTY its own process holds, and it cannot know that in advance: a session started by `paseka bee chat` in another terminal is `active` with a live PID and looks identical on the list. So the relay is asked, and the server's reason is translated — verified against a live console, where the socket opens, the server answers `{"type":"status","state":"exited","reason":"sessions: session \"…\" not active in this process"}` and closes 1008 with the same text. The legacy showed that Go string under a frozen terminal with Stop and Resume hidden, because the session still read as active.

**Resume is one control, and it is never silently absent.** It needs the continuation typed beside it, so it lives with that box rather than duplicated in the header; the legacy's resume input sat outside any form, so typing a line and pressing Enter did nothing. An adapter that cannot resume, or a provider that never reported a session id, are each *reasons* — the legacy hid the control for the first and showed a bare "No provider session id" for the second, so both looked like nothing to click.

**The transcript follows the reader, not the clock.** The legacy re-rendered every line of a session on every tick with no cap, and forced `scrollTop = scrollHeight` each time, so a transcript could never be scrolled up: the moment an operator reached for a line, the next poll took it away. Lines are kept to a tail with the count of what was dropped, the view follows the newest line only while the reader is already there, and a **Latest** button appears the moment they are not. It does not wrap either: this is a terminal, and the real session here holds a two-column slash-command menu that wrapping folds into a staircase.

### Runs

- **Functionality:** Headless adapter runs from `paseka run` and spawned bees; detail shows metadata, summary, and a raw event list.
- **Components:** run list, run detail (meta `<dl>`, summary `<pre>`, events `<pre>`).
- **Design proposal:** Keep, compact. Consider making it a scoped filter of the Traces detail (runs for a trace) rather than a top-level tab. Render events as a readable list instead of a raw `<pre>`.
- **Implemented:** `/next/runs` and `/next/runs/:traceId/:agentId` keep both, and the list stays a top-level route rather than a filter inside the trail detail — a run is reachable from three directions (the list, a trail, and a bee), so making the trail the only way in would add a step for two of them. The list is five columns and compact as proposed: the adapter is **searchable rather than shown**, because a sixth column of identifiers is what pushed the run's own link off the right edge, and the trail column takes `grow` so it truncates instead. **Events are the readable list, not a raw `<pre>`** — the run's events endpoint hands back raw `protocol.Event` envelopes, so `runEventSummary` derives the contract, payload kind, severity, and summary, and each row is the same `SignalCard` the Dashboard and the Timeline feed already use. A payload with no `summary` still says something: `payloadDigest` lists the payload's readable fields, and a **list of records contributes its first element**, because `artifact.written` announces `{"artifacts": [...]}` with no top-level scalar and rendered as a blank row until that was handled. The raw envelope stays one folded disclosure away on the row, costing no request. **There is no paging control on a run's events**, and that is the finding rather than an omission: `runs.Dir.readEventsFrom` returns `all[skip:]` with no server-side cap, so the first read is already the whole log and `nextCursor` is an index rather than a promise of more — a button could only ever confirm there was nothing left. The run summary stays literal text in a scroll box, since whatever the adapter wrote includes terminal escapes, and the task body is folded because reading a run is about what it did. **Prev/next within the trail** step by start time rather than list position, so a fresh run does not shift what "previous" means, and a run outside the recent window reports no position rather than a confident `1 of 1`. They are real links, not buttons that swap the store: a run has its own URL, so stepping to a sibling has to put that URL in the address bar or the run cannot be shared and Back misbehaves. This is the one route that **polls** (5s) among the read-mostly pages, because a run's state moves from queued to running to completed while an operator watches. A deep link to a run older than the recent window fetches the run directly rather than rendering blank.

### Topology

- **Functionality:** Static colony EDA topology graph (cytoscape) derived from bee YAML and `auto_invites`; summary cards, Copy Mermaid, Refresh, Reset layout.
- **Components:** cytoscape graph container, topology summary, action buttons.
- **Design proposal:** Keep, but treat as informational — move it under Diagnostics (with System) rather than a top-level tab. Collapse Copy Mermaid / Reset layout behind an actions menu; only Refresh stays visible.
- **Implemented:** `/next/topology` keeps the graph and the Diagnostics grouping, and the three actions stay visible — the proposal to hide two of them behind a menu is declined. A menu is right for controls an operator uses occasionally, but Copy Mermaid and Reset layout are both reached for *while looking at* the graph, and a menu puts them a click further from the thing they act on. cytoscape moves from the legacy bundle's vendored UMD into the new frontend as a real dependency, pinned to 3.31.0 — the first release that ships its own types, so the graph is type-checked rather than `any`; the legacy stays on its vendored 3.30.4 and the two graphs are not byte-identical, which is fine because both are derived from the same projection. It is **imported dynamically** so its ~400 kB lands in this route's chunk instead of the initial bundle every route pays for. Its `exports` map has no `types` condition, so TypeScript never sees the bundled declarations; rather than a `tsconfig` `paths` override (which would replace SvelteKit's generated `$lib` aliases rather than merge with them) there is one local `cytoscape.d.ts` declaring the surface the graph calls. **Colours come from the theme.** cytoscape is imperative and needs concrete colours, which is the one place the design system's no-literals rule is bent, so `topology-theme.ts` reads the active DaisyUI custom properties and maps them onto cytoscape's properties: a Svelte file carries token *names* and no hex, and a theme switch restyles the live instance instead of rebuilding it, which would discard the operator's in-progress drag. The legacy's hard-coded dark palette is gone, and the four contracts keep one hue each by mapping SIGNAL/INSIGHT/MUTATION/VERIFICATION onto `info`/`secondary`/`warning`/`success` rather than inventing colours. The line language is unchanged — solid subscriptions, dashed publications, dotted invites, a faded edge for a rule the bee never declared — so the graph reads the same as it did. **The layout was rebuilt rather than ported.** The legacy measured each node's label-inclusive bounding box, which needs a laid-out canvas and cannot be unit-tested; here the element set, the barycentre ordering that cuts edge crossings, and the positions are pure functions in `lib/topology.ts`, tested without a canvas. Bees stay in one left column while event kinds wrap into a block whose aspect roughly matches the viewport: a single row of fourteen event ids is a line several thousand pixels long, and the `fit` that framed it shrank every label to nothing — the first version of this migration did exactly that, and also stacked all seven bees on one point. A dragged shape persists to `localStorage` under a key namespaced by colony, and *Reset layout* clears it so it cannot come back. The canvas is opaque to a screen reader and cannot be pasted into a PR, so the container's label carries the size and points at the Mermaid block, which is the same graph in the form `paseka colony topology` prints.

### System

- **Functionality:** OS/container view of the Queen process (PID namespace inside Docker): host identity, metrics (CPU, RSS), process table.
- **Components:** identity `<dl>`, metrics cards, `system-process-table`, Refresh.
- **Design proposal:** Keep as a Diagnostics-style page grouped with Topology under a "Diagnostics" menu section. Auto-refresh metrics periodically instead of a manual Refresh. Hide the process table under an expandable block.
- **Implemented:** `/next/system` keeps the Diagnostics grouping and takes both proposals: there is no Refresh button, because the page has no mutations and a control duplicating a 5s timer only teaches the operator to distrust the number, and the process table starts folded with `25 busiest` in its summary line. The metrics lead as `StatTile`s because that is why the page is opened, and they carry what the topbar Host plaque cannot — available memory, load 5 and 15, and colony disk — while the identity block below is a `MetaList` whose rows are the values an operator pastes into a bug report (hostname, console pid, Go version). A metric tile appears only when the server measured it, so a failing `statfs` leaves the block quiet instead of padding it with dashes; CPU is the deliberate exception, since its percent is a delta between two `/proc/stat` samples and its first-sample gap is expected, so the tile stays and explains itself in a `Hint`. The process table needed its own byte formatter: the GiB one the tiles use prints `0.00 GiB` down an RSS column of MiB-sized processes, so the unit follows the value and never climbs back to GiB. The legacy console marked a live adapter with a row class; here the `Source` column declares a `badge` that returns `live` for a pid the Live bees panel reports and `null` otherwise, read from the chrome stream the topbar already keeps rather than a second request. Two CPU numbers share the page with different denominators — the tile is whole-machine and caps at 100%, a row is per-core and reads 172% — and the block says so, because otherwise the table looks broken beside a tile reading 15%. `systemStore` polls `/api/system` at 5s (the busiest read in the console, since it walks every pid) and keeps the last good snapshot when a read fails, so the numbers an operator is reading stay on screen as stale rather than blanking; a failed read is an `alert-error` while the server's partial-failure string arrives on a 200 and is an `alert-warning` about missing rows. The Host and Git plaques are now links to their own routes, which the legacy console had as whole-panel click targets.

### Git

- **Functionality:** Colony clone vs origin: Fetch / Push / Pull (ff-only) with hooks toggle, unpublished commits, branches table (Delete merged leftovers). The worktrees table and the Prune orphans action were here first and now live on the Worktrees route.
- **Components:** origin meta `<dl>`, action buttons, branch table, unpublished commits list.
- **Design proposal:** Keep the operational sync controls (Fetch/Push/Pull) where they are, but split the worktrees list into a dedicated Worktrees route (user story #8). Group branch/worktree maintenance actions under a "Maintenance" dropdown.
- **Implemented:** `/next/git` keeps the operational controls where the operator expects them and splits the read-only half off: the page owns colony-root-versus-origin, the unpublished commits, and the leftover-branch sweep, while the read-only worktree list is what the still-placeheld `/next/worktrees` route will take. The two proposals that did not survive review are recorded rather than silently dropped. The sync actions are a compact `btn btn-sm` group in the page header — the legacy row stretched three equal-width buttons across the panel — with the push-hooks flag as a `toggle toggle-xs` beside them, and **Push takes `btn-primary` only while there are commits to publish**. Fetch/Push/Pull fire on one click because the server already guards them; **Prune orphans** and **Delete N leftovers** destroy local state, so they open a `Modal` first and the delete dialog names every branch it is about to remove. The **Maintenance dropdown was dropped**: each action already sits alone in its own section header, so a dropdown would hide two destructive controls behind an extra click and buy no density. Per-row branch delete is also gone — `DataTable` cells are declarative, so a button in a cell would need a capability no other table has justified yet, and the leftover sweep is the operation the section exists for. The clone splits into two one-column lists (*Colony root* beside *Origin*) because one two-column grid paired unrelated rows; a row appears only when it says something, the divergence numbers live inside the sync word rather than repeating as `Ahead`/`Behind` rows, and the server's `Note` is kept as a row because without a remote-tracking ref the server omits the unpublished list and an empty publish list would otherwise look like there is nothing to push. Worktrees and branches are `DataTable`s whose path stays in `searchText` (it is derivable from the trace id), each row badged with one word — a worktree `dirty`/`clean`, a branch `current` → `leftover` → `merged` — and a branch's commit subject is the `grow` column, because giving the leftover width to the branch name starves the prose. An empty publish list drops the section entirely; the `Sync` row already says `in sync`. `gitStore` polls `/api/git` at 15s rather than the legacy 3s, since every read shells out to `git` several times, and re-reads the clone after each mutation; there is no manual Refresh and no per-route Git state in the topbar plaque, which rides the chrome stream. **The worktree table left after all that**, taking the orphan prune with it: `/next/worktrees` owns both, and this page keeps a count with a link in their place. The branch table keeps the worktree path and the trail behind a branch in its `searchText` even so, because a row here is a branch, and a worktree is only one of the things that can hold one.

### Worktrees

- **Functionality:** The colony's isolated worktrees — one row per checkout under `.paseka/worktrees/<traceId>/` with its branch, base SHA, dirty state, and pull request — plus the one verb that reconciles them with the registry: prune orphans.
- **Components:** worktree table (lifted off the Git page), a prune action and its confirmation, the per-trail links a row can carry.
- **Design proposal:** Take the worktree table off `/next/git` and own it here, prune included. The Git entry above already promised the split; what the split is *for* is three things that page cannot be.
- **Decided:** Prune moves with the table, because it is the verb that resolves what this page lists. The Git page keeps a count and a link in the table's place, and the Dashboard's active-worktrees tile links here, so the list is never the orphan. The data stays on `GET /api/git` — the worktree list is already built inside it, and no new endpoint is added; Git and Worktrees are never mounted at once, so one route-scoped store serves whichever route is open instead of a second poller on one URL. The page is a `DataTable`, and `WorktreeCard` comes out of the component inventory: the Git migration already showed this row wants a table. The page promises no per-row action and no orphan badge. `DataTable` cells are declarative, so dropping one worktree or deleting its branch is a table action intent no second table has asked for; and the server's snapshot deliberately drops any row that is no longer a checkout root, so an `orphaned` badge would be the client inventing a state it was never sent. The list shows live checkouts, and the prune result names what it reconciled.
- **Why the split, in three reasons:**
  1. **The verbs are unrelated.** Everything else on the Git page answers "what is published" — Fetch, Push, Pull, unpublished commits — and none of them reads a worktree: Pull explicitly ignores isolated worktrees, and the prune confirmation states that branches are kept. The cleanup destroys neither refs nor origin state; it reconciles the home registry and `.paseka/worktrees/` against the disk. A destructive verb sharing a header with Push, one click away, is the reason to move it rather than keep it.
  2. **The list is a reconciliation, not a status read.** The server builds it from the home registry, `git worktree list --porcelain`, and the on-disk directory, and then drops whatever is no longer a checkout root. The interesting rows are the disagreements — registered but gone, on disk but unregistered, branch against a `worktree.branch` insight — while the Git page's other blocks are single-source reads. A page whose subject is where the registry and the disk disagree needs its own filters and its own empty and partial states, not a slot under three sync buttons.
  3. **The row is keyed by trail.** A row is `traceId` → branch, base SHA, PR URL, dirty. Its neighbours are the trail detail's worktree block, the review's merge diff of that same branch, and the pull request; the branches table is a different population — every local branch, including merged leftovers and ones no worktree holds. After the split this page is a trail-shaped list: one row per trail that has a checkout, linking out to the trail and the PR.
- **Implemented:** `/next/worktrees` is that inventory, and the split landed with it. The page is a header — the headline sentence beside the prune button — over a `DataTable` of exactly the rows the Git page used to carry, because a page with one section does not also want a section heading saying what its `<h1>` already said. **The headline is a sentence in three forms, not a count with a plural**: a colony with no worktree has not isolated anything yet, which is a different claim from having isolated none of several. **Prune moved with the table and the Git page kept a count and a link where its own copy was**, so the list is never the orphan — and that section is absent entirely when the colony holds none, because a heading over an empty sentence says nothing while the Dashboard's active-worktrees tile is the count's real home, now that it links here too. **The store is the Git store, unchanged**: the worktree list was already inside `GET /api/git`, and two routes that are never mounted at once are what keep one endpoint on one poller. **`WorktreeCard` came out of the inventory and the table stood as it was** — same columns, same `grow` branch, same `dirty`/`clean` badge, same empty pull-request cell — because moving a table between routes is not a redesign of it. Two things the move did force. The column reads **Trail**, not Trace, now that a row is keyed by one; and **the server's prune message no longer opens with a space**, because `git worktree prune` prints nothing when it had nothing to do and the console toasts that message verbatim — the parts are joined rather than concatenated, and the Go test asserts the exact string. What the page does *not* promise is unchanged from the decision: no per-row action, and no `orphaned` badge, because the snapshot drops a row whose checkout is gone and the client would be inventing a state it was never sent.

### Bees

- **Functionality:** None in the legacy console. The colony's bees appear only as two `<select>` dropdowns (`GET /api/bees` read once at boot, offering `role (adapter)`), as graph nodes on the Topology tab, as a `bee` label on runs, traces, tasks, invites, and sessions, and as the topbar's *Live bees* plaque, which routes to Runs or Sessions and never to a bee.
- **Components:** none; the page is new.
- **Design proposal:** It is the first route the redesign **invented rather than ported**, so it needed a scope decision before any markup, and [the migration backlog](docs/plans/ui-migration-backlog.md) is explicit that parity cannot be its acceptance criterion. The user story asks for "all registered bees with status, last run, and adapter info", which is a health page, and the audit's `BeeCard` was a guess at its shape.

- **Decided:** The page is a **roster, and a roster is not a launch picker.** `GET /api/bees` was written for the forms — it drops every bee whose adapter cannot be started as an interactive session, so a colony of `script` bees answers `[]` — and a page whose subject is the colony's inventory cannot be built on an endpoint that hides a third of it. So the endpoint grew a `scope` and the **default stayed the picker**: an absent `scope` is `launchable`, which is what both drawers and the legacy console already read, so a client that never learns the parameter still cannot offer a bee it could not start. `?scope=colony` is every bee, each carrying an `interactive` flag so the page can say which rows have no session behind them. `colony.Bee.Sector` was documented, present in every bee YAML, and reachable from **no** console surface at all, so it is on the view now too.

- **A last run is the one thing the client could not be trusted with.** The obvious build is to group `GET /api/runs` by `bee` on the client, and it is wrong: that endpoint is capped at the 50 most recent runs colony-wide, so a busy colony reports a quiet bee as having **never run** — the same class of lie as the `orphaned` badge the Worktrees page refused. So the server derives it, from `runs.ScanRuns`, which is the same walk `ScanRecentRuns` already paid, uncapped, newest first, first run per role wins. Splitting the two is the whole backend change: `ScanRuns` is the walk, `ScanRecentRuns` is the walk plus the truncation, and the Go test asserts the split rather than trusting it.

- **Implemented:** `/next/bees` is that roster, as a `DataTable` — so **`BeeCard` is out of the inventory**, the same call `WorktreeCard` got, because a bee is one line of facts. Columns are Bee (`mono`), Adapter, Intents (`secondary`, `grow`), Sector (`secondary`), Workspace, Live, and Last run. **Intents are one comma-joined string rather than a badge each**, and that is the `DataTable` contract deciding it: `text` is the only text intent there is (a Svelte snippet cannot be built inside `<script>`) and it always feeds the filter box, so the join makes every intent individually searchable for free, where badges would want the vocabulary duplicated into `searchText` by hand *and* the row to grow, which `whitespace-nowrap` forbids. The separator is `, ` because the values are a set of identifiers, the same call `traceBees` and `task.dependsOn` make; `·` is for a phrase built from parts of one thing. A bee with no templates dashes rather than blanking, because a blank cell is what a row still loading looks like.

- **Three columns are three different kinds of absent, and each was decided.** **Live** is a badge fed by the agents frame the topbar already keeps — the `/next/system` precedent, so it costs no request and cannot disagree with the plaque — and a null badge is the empty cell, because "no live process" is most rows most of the time and a word in each would be noise. **Workspace** is plain text, because it is committed config rather than a state that moves, and the row that most needs saying out loud is `worktree: false`: a bee that writes to the colony root, which a badge column would have left empty. **Last run** is a link to the run page with the state badged beside it, and a bee that has never run gets an **empty** cell — the declared-but-null badge, which is the contract's own answer, rather than a dash that would read as a missing timestamp.

- **The page does not poll, and the live column is why that is not a gap.** Everything static here comes from committed bee YAML, so it changes when a commit lands — the topology route's reasoning. The one fact that moves is liveness, and it arrives on a stream rather than a timer. Refresh stays because a **run landing** is the one thing on this page that changes without a commit, which makes it the honest control rather than a missing feature.

### Settings

- **Functionality:** None in the legacy console — its ten tabs are Dashboard, Traces, Timeline, Tasks, Reviews, Sessions, Runs, Topology, System, and Git, and none of them is a settings surface. The only thing a legacy operator had was the theme stored in `localStorage` under a key the legacy bundle shares with Topology node positions, and the ability to edit YAML by hand.
- **Components:** `ThemeSelect` (already in the inventory, unused until now); the page is otherwise new.
- **Design proposal:** User story #9 asks for "themes, NATS endpoints, API keys, and notification preferences, so that I can customize the console **without editing files**". Three of those four do not exist anywhere as a console surface, so this is the second route the redesign **invents** rather than ports — after Bees — and the migration backlog is explicit that parity cannot be its acceptance criterion.

- **Decided, in three parts. The scope, the source, and the refusal.**

  1. **The route's scope is the effective configuration, and it is read-only by design rather than by omission.** NATS endpoints and notification preferences are real settings, but writing them needs a capability the codebase does not have: `internal/colonyinit` is the only writer of `colony.yaml` and the home `config.yaml`, it is reachable only from `paseka init`, and it is create-only by construction — `writeFileIfMissing` returns without touching a file that exists. A console write path is therefore new platform capability, not one more endpoint this migration adds, and **it is out of scope for the redesign**: what ships here is the read half, a page that says what every setting currently resolves to, plus the theme picker that already worked. The page says it is read-only rather than offering controls whose endpoints do not exist, because a control that looks editable and silently does nothing is worse than no control. The write side is tracked in [Backlog](../plans/backlog.md) as a capability of its own, where it wants its own spec; user story #9's "without editing files" is the half this spec does not claim.

  2. **Every value carries the source that decides it, and that is the whole design.** `colony.NATSConfig.EffectiveURL` prefers `PASEKA_NATS_URL` over the home config, `BotToken` prefers `PASEKA_TELEGRAM_BOT_TOKEN` over the file, and `selectedProfileName` prefers a `--profile` flag, then the environment, then the home config's sticky `profile:`. A settings page showing values alone would therefore report a NATS URL the process does not use, and an operator editing `config.yaml` would watch nothing change with no explanation. So the endpoint answers `{ value, source }` per setting, where `source` is one of `config.yaml`, `colony.yaml`, `default`, `unset`, `env:NAME`, or `flag`. This is the same rule the bees roster and the worktrees inventory applied — the client is never left to infer a state the server did not send — applied to provenance rather than to a derived field. A default is labelled in the cell rather than in a `Hint`, because a value nobody wrote must not hide behind a hover; `config.yaml` itself is left unannotated, being what an operator editing the file expects.

  3. **The refusal is the part a settings page earns its keep on.** An environment variable outranking the file is exactly the case where a write must be a **409 naming both sources** rather than a success that changes nothing — the precedent `git.Pull` already sets. And the secrets model is not negotiable in a browser form: adapters store `api_key_env`, a *variable name*, and read the value from the environment at call time, so the page reports the name and whether it resolves and never receives a key. `botTokenSet` is the gate's equivalent. The Go test asserts the raw response body carries neither secret, because a struct-level assertion would not catch a field added later.

- **A declared adapter value and a loader default are two different things, and the file is the only one that can tell them apart.** Every adapter loader fills a default for an absent key — `cursor.yaml` holding only `binary` still yields `api_key_env: CURSOR_API_KEY` — so a loaded struct cannot attribute a value to a file. Attributing it to the file anyway would send an operator to a line of their YAML that does not exist, which is a worse lie than showing no source at all. So `colony.AdapterConfigDeclared` reports which top-level keys `adapters/<name>.yaml` actually sets, and the view marks each value `config.yaml` or `default` from that. A file that does not parse is reported as absent: the loader already fails on it in the request path, and this must not become a second, quieter error.

- **The gate has to be reportable while broken, and `telegram.Load` cannot do that.** `Load` treats a missing `telegram.yaml` and `enabled: false` as *errors*, so reading the gate through it would render "the gate is switched off" as a failed read — the one answer an operator most needs. `telegram.Inspect` parses and applies the same defaults and the legacy `waiting_review` mapping without validating, and reports presence separately from enabled. The legacy `waiting_review` key is folded into the two review categories on read and never appears as a category of its own, so the page shows the seven the gate actually acts on rather than a key that is a synonym for two of them. `internal/console` gaining an import on `internal/gate/telegram` is a new edge, and it is the right one: the schema belongs to the package that owns the gate, and a second copy of it in the console would be the thing to regret.

- **Implemented:** `GET /api/config` and `/next/settings`. Transport, Appearance, Adapters, Human gateway, Colony — no new component, since `Section`, `MetaList`, `DataTable`, `DetailRow`, and `ThemeSelect` between them already cover a page of short labelled lists. The adapter table is the eighth `DataTable` and adds nothing to the inventory. Push modes are `DetailRow`s with a `StatusBadge`, which is the right primitive: a category is one line of facts with a value beside it, not a table row. **The three push modes got rows in the tone table** rather than local classes, read as "will this interrupt me": `sound` takes the attention tone because it is the only mode that alerts, `silent` takes the in-flight one because it delivers quietly, and `off` takes the idle one because it is the absence of a push. That is the design system's own procedure — a new domain status gets a row, not a class in the component showing it — and it means a settings page cannot invent a palette beside the rest of the console.

- **The page does not poll, and this is the third time that reasoning has been reached.** A bee roster is committed YAML, the topology is `auto_invites`, and configuration is a file edited by a human: all three change when something outside the process happens, so a timer would re-read identical values forever. The one fact that does move under a running process — whether NATS is *connected* — arrives on the chrome stream the topbar already keeps, and the page reads that rather than asking the server a second time, which the store contract forbids. The endpoint therefore reports configured values and their provenance, and **not** liveness. Refresh is the honest control, and a failure keeps the last good snapshot: the values an operator is reading are still the last real ones, and the alert says they stopped moving.

- **Two defects the fixtures hid, which is why the test asserts the raw body.** Running the endpoint against a live colony is what found them. `ConfigProfileView` first embedded a `colony.ProfileLayers`, which carries no JSON tags and marshalled as `Colony`/`Home` in an otherwise camelCase API — the TS type claimed `colony`/`home` and would have read `undefined` for both. And every list was a nil slice, so an absent gate answered `"allowFrom":null, "chatIds":null, "notify":null`. Both are the class `runs: null` and `taskCounts: null` already taught this API about, and both are invisible to a fixture that returns `[]` and `{}`. The Go test now greps the response body for `:null` and for Go field names, rather than decoding into a struct that would normalize both away.



## Implementation Decisions

- **Framework**: Svelte 5 with SvelteKit for file-based routing; app components use runes syntax. The global `runes` compiler flag stays off so legacy-mode dependencies such as `lucide-svelte` compile. SSR is disabled for SPA mode and the static adapter produces an embeddable fallback page.
- **Frontend isolation**: The redesign lives in a dedicated top-level frontend module with its own pnpm lockfile and build lifecycle. The legacy vanilla JavaScript console remains a separate, untouched bundle until cutover.
- **URL coexistence**: The redesigned application's base path is `/next`. `/next/` and its routes such as `/next/dashboard` are served by the new bundle; `/next` redirects to `/next/`; `/` continues to serve the legacy console. SPA fallback is confined to the `/next/` prefix so a missing preview asset cannot change legacy routing behavior.
- **Styling**: Tailwind v4 uses its CSS-first configuration and first-party Vite plugin. DaisyUI 5 is loaded from the main stylesheet. The initial theme set is limited to `catppuccin-latte`, `catppuccin-frappe`, `catppuccin-macchiato`, `catppuccin-mocha`, `light`, and `dark`.
- **Theme switching**: A `data-theme` attribute on `<html>` is driven by a Svelte store persisted to `localStorage`; DaisyUI owns the resulting CSS variables.
- **Layout shell**: The root application layout renders the top status panel, the responsive left-side menu, and the routed main content. Below 768px, the left menu becomes a bottom sheet.
- **Top panel**: Carries legacy parity as a single row. The identity block shows the console name, the colony slug, and a `StatusIcon` for the NATS transport (link glyph connected, broken glyph disconnected, dashed glyph when NATS is not configured). Four bordered panels follow — Hive runtime, Live bees, Host, and Git — each with its label, status on the right, and brief detail (runtime pid/started/heartbeat, bee counts, host CPU/memory/load, git sync state/branch/head/fetch age). Review and invite attention badges appear inline only when pending. The active trail count is not in the top panel; it belongs to the Dashboard route, fed by the same dashboard poll as NATS. The existing console status stream supplies runtime, agents, host, git, and attention; a dashboard poll supplies NATS and active trails. Queen version is deferred until the API exposes it.
- **Routing**: Application routes are Dashboard, Traces (`/next/traces` plus the detail child `/next/traces/:id`), Timeline, Tasks, Reviews, Sessions, Bees, Worktrees, Runs, Git, Topology, System, and Settings beneath the `/next` base path. A menu entry stays active on any child of its path. A route whose body needs its own props keeps that body in a sibling component and leaves `+page.svelte` reading `page.params`, so the page is testable without a router. The side menu groups them as Work (Dashboard, Traces, Timeline, Tasks, Reviews, Sessions), Colony (Bees, Worktrees, Runs, Git), Diagnostics (Topology, System), and Configuration (Settings); every route resolves to a `PagePlaceholder` until its section is migrated. Authentication behavior must match the existing console rather than introducing a new login boundary during the redesign.
- **API layer**: A central typed client calls the existing root-relative `/api/*` endpoints; the `/next` URL prefix applies to frontend routes and assets, not the API. TypeScript payload types are generated from Go event contracts. `lib/api/client.ts` is the only module that fetches; it raises `ApiError` carrying both the HTTP status and the server's plain-text reason, because a domain message like `honey reserve not configured` is the whole point of a 503. Callers render `error.message` and leave the transport banner to the topbar. `GET /api/traces` grew `limit` (clamped 1..200) and `before` so the Traces route can page past the old hard cap of 20; the projection order is now total, tie-broken by trace id, so a cursor boundary walked twice cannot skip or repeat a trail. The cursor is anchored to a trail rather than a rank, which is what keeps a page stable while the colony keeps producing new ones. A `cursorPageScanLimit` of `limit * 10` came off with it: there is no index over `.paseka/runs`, so the scan is a full walk whatever the page asks for, and the cap was filtering rows the walk had already read — it capped the walk at ten pages and reported that the history had ended there. `GET /api/bees` grew `scope` — absent or `launchable` is the picker, `colony` is the roster — and the default is the picker so a client that never learns the parameter still cannot be handed a bee it could not start; the colony scope adds `interactive`, `sector`, and a server-derived `lastRun`, and skips it on the picker so opening a launch drawer does not walk every run directory in the colony. `runs.ScanRuns` is the unbounded walk and `runs.ScanRecentRuns` is that walk plus a truncation, because a per-bee last run cannot be reached through a recent-page cap. `GET /api/config` is new and read-only for the whole redesign: it reports the effective configuration with the source that decides each value, never a secret, and it is the only endpoint that answers "where did this come from" — the env override of `nats.url`, the adapter loader defaults a `yaml.Node` has to distinguish from declared values, and the Telegram gate's presence as distinct from it being enabled. It reports no liveness, because the topbar's chrome stream already carries that.
- **State management**: Svelte 5 runes (`$state`, `$derived`, `$effect`) handle local state; small cross-route stores handle theme, status, and trail data. The console status store owns the **only** poll of `/api/dashboard` and keeps the whole `DashboardSummary`, so the topbar's NATS badge and the Dashboard route read the same snapshot; a second poller for the same endpoint is a bug. A route-scoped store may own a *different* endpoint and must start on mount and stop on unmount, so an idle console holds no poll — `tracesStore` polls `/api/traces`, `traceStore` polls `/api/traces/:id`, `gitStore` polls `/api/git`, `systemStore` polls `/api/system`, `runStore` polls `/api/runs` and `taskStore` polls `/api/tasks` because a run's and a task's state are both live, `reviewStore` polls `/api/review-queue` because a review queue is the thing an operator waits on, and `timelineStore`, `topologyStore`, `beesStore`, and `settingsStore` poll nothing at all — the event feed is paginated history, the topology and the bee roster are both derived from committed config, and configuration is a file a human edits, so in those cases a timer would fight the operator and a deliberate Refresh is the honest control. A bee's liveness is the exception that proves it: it does move, and it is joined from the chrome stream the topbar already keeps rather than from a second poller. A store assigns a payload only after checking it is still the answer being waited for, so a slow read for a trail the operator left cannot overwrite the current one. Store getters are reserved for derived values (`natsStatus`, `activeTraceCount`); pass-through fields are read off `store.dashboard` directly. `refresh()` forces an out-of-band poll for a route that just mutated. One mutation is in flight per store: `gitStore.run()` answers `busy` rather than queueing, because push, pull, branch delete, and prune all write inside the same clone and would race on the repository's own locks — a UI-level guard against two clicks, not the lock against live bees, which stays in [Backlog](../plans/backlog.md).
- **Component library**: Shared DataTable, StatusBadge, StatusIcon, SignalCard, TraceRow, StatTile, Section, MetaList, DetailRow, EnergyMeter, ArtifactViewModal, CueRunModal, Modal, Drawer, Toast, and ThemeSelect components use DaisyUI primitives and Tailwind utilities. StatusIcon renders a `lucide-svelte` icon on `currentColor` and replaces StatusBadge where the label already names the subject, keeping the raw status as its accessible name. DataTable is generic over its row type; a cell is declarative — `text` is what the cell shows, `searchText` adds terms that are searchable but not shown, `href` renders a link and may return `null` for a row with nowhere to go (plain text, not a link to nothing), `badge` renders a StatusBadge (or nothing when it returns `null`, and a column that declares `badge` and gets `null` leaves the cell empty instead of falling back to `text`), one `grow` column takes the leftover width so it truncates — its text truncates with it, or it overflows its own cell — and a `secondary` column hides below 768px. `mono` sets a monospace face for refs, SHAs, and paths. There is deliberately no `cell` snippet: a Svelte snippet cannot be constructed inside `<script>`, so it was unusable from a page — and for the same reason there is no per-row action button, which is why a destructive action lives in a section header rather than on each row. Cells never wrap — a wrapped date doubles the row height, and the one `grow` column truncates instead, so prose takes the leftover width. `StatTile.hint` is a `string[]`, matching `MetaRow.hint` and `Hint.lines`, so a caller with two lines of explanation does not have to join them into one sentence. A page may read another store it does not own: `/next/system` marks live adapter processes from `consoleStatusStore.agents.items`, the chrome stream the topbar already keeps, which is a read and not a second poller, and `/next/bees` counts a bee's live workers from the same frame. A **multi-valued cell is one joined string**: `text` is the only text intent there is, so `beeIntentsLabel` comma-joins a bee's vocabulary and every value becomes individually searchable through the filter box, where a badge per value would want the list duplicated into `searchText` by hand and the row to grow, which the no-wrap rule forbids. A domain status that is missing from the tone table falls through to `neutral`, so a new status gets a row in the design-system contract rather than a local class in the component that shows it; the trail surface added `planned`, `queued`, `completed`, `blocked`, `cancelled`, `announced`, `staged`, `standing`, and `low`, and the Git route added `clean`, `dirty`, and `leftover`.
- **Form pattern**: Create/edit forms use a Modal or Drawer triggered from the current list or grid; they never replace a full column. Both variants trap focus, close on Escape, and restore focus to their trigger.
- **Worktrees route**: `/next/worktrees` is the inventory of the colony's isolated worktrees and owns the orphan prune; `/next/git` keeps colony-versus-origin, the unpublished commits, and the branch table, and carries a count with a link to Worktrees where its worktree table used to be. Both routes read the same `GET /api/git` — the worktree list is already part of that view and no new endpoint is added — and they are never mounted at once, so the single route-scoped store serves whichever route is open rather than putting a second poller on one URL. The page is a `DataTable`, so `WorktreeCard` left the component inventory. Columns are Trail (a link to the trail detail, plain text when the row has no trail to open), Branch (`mono` and `grow`, with the worktree path in `searchText` because it is derivable from the trail id), State (`dirty`/`clean`), Pull request, and Base SHA as `secondary`. Prune is a header action behind a `Modal` keeping the wording it shipped with — what it drops, and that branches are kept — and its result is reported through a `Toast`. The page promises no per-row action, because `DataTable` cells are declarative and dropping one worktree is a table action intent that belongs where the first table needs one; and it reports no per-worktree registry state, because the server's snapshot drops a row whose checkout is gone, so the reconciliation shows up in the prune result rather than as a badge the client would have to infer.
- **Runtime control**: The Hive runtime panel carries a single icon control instead of Start/Stop buttons. `runtimeAction()` maps the runtime status to exactly one action: `stopped` and `stale` map to start (the supervisor clears a stale registry entry itself), `running` maps to stop, `stopping` maps to blocked, and every other value (`starting`, `degraded`, unknown, or a missing frame) maps to an explicit chooser. `stopping` must stay blocked because `Supervisor.Start` only skips spawning for `alive && running` — calling it mid-shutdown would start a second runtime. The icon is the action and inherits the button colour rather than the status tone (play, stop square, spinner, dashed circle), the accessible name spells the action out, and the panel keeps the three-line shape of its siblings: the raw status word with a hint for the unusual values on the second line, the live `heartbeat · pid · started` detail on the third. Times are always 24-hour regardless of the browser locale, and every truncating line carries a `Hint` popover with the full text on separate lines. Stop is destructive and opens a `Modal` confirmation; the ambiguous state opens a `Modal` with both Start and Stop. The returned runtime view is applied immediately instead of waiting for the next chrome frame, overlapping actions are ignored, and the result is reported through a `Toast`.
- **Build lifecycle**: The frontend exposes `dev`, `build`, `check`, and `test` pnpm scripts. Development runs at the `/next/` base path and proxies root-relative API traffic to a separately running Go console. Production build output is written into the Go embed tree and embedded independently from the legacy assets.
- **Build safety**: The generated production bundle is committed with the Go module so `go install` remains a complete single-binary deployment. A checked-in preview fallback keeps source-only Go builds compilable, while release and container builds refresh the frontend before compiling Go. The legacy bundle is never removed or redirected by the frontend build.
- **Testing**: Vitest and Testing Library cover stores and components; Playwright covers end-to-end behavior. Go route tests verify `/next` redirect behavior, preview SPA fallback, missing-asset 404s, unchanged legacy root behavior, and unchanged API routing.
- **Accessibility**: Use semantic HTML, ARIA labels for icon-only controls, visible focus states, and color-contrast-compliant DaisyUI themes.

## Out of Scope

- Real-time collaborative editing or multi-user cursors.
- Plugin/extension system for third-party panels.
- Historical analytics charts (Grafana/Prometheus integration remains separate).
- Mobile app or PWA offline support beyond localStorage persistence.
- Migration of existing console code — this is a clean rewrite.
- Replacing, redirecting, or removing the legacy console at `/` before feature parity and explicit cutover approval.
- **Writing colony configuration from the console.** User story #9 asks for NATS endpoints, API keys, and notification preferences to be configurable "without editing files", and the read half of that ships as `/next/settings`; the write half is a platform capability the codebase has never had rather than a route, since nothing outside `paseka init` writes `colony.yaml` or the home `config.yaml` and that writer is create-only. It is tracked in [Backlog](../plans/backlog.md) and wants its own spec. The console is therefore read-only about the colony's own configuration, and the page says so rather than offering a control that would change nothing. Credentials are outside that item too: the credential model stores a variable *name*, and both the read endpoint and the runtime adapters read the value from the environment, so no key enters the colony config in either direction.

- Keep the theme list at the six curated themes; add or remove themes only with an explicit design decision.
- Consider `svelte-put/clickaway` and `svelte-put/escape` for menu/drawer interactions.
- Go binary size impact: embedded SPA ~2–3 MB gzipped; acceptable for single-binary distribution.
- Delivery is phased: embeddable frontend foundation and preview route, application shell, feature-by-feature parity, then an explicit root cutover that removes or archives the legacy bundle. Foundation, shell, Dashboard, Traces (list plus detail), Git, System, Timeline, Topology, Runs, Tasks, Reviews, Sessions, Worktrees, Bees, and Settings are all done, which means no route resolves to `PagePlaceholder` and the preview has closed every surface the legacy console had — plus two the legacy never had.
