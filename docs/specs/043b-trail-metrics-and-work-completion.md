# Spec 043b: Trail metrics and work completion

## Status

**(Implemented)**
Second half of the 043 split, paired with [043a](043a-truthful-run-records.md). Five primitives make a trail readable by code: cue provenance, a versioned trail metrics projection, the `trail.work.completed` milestone, execution purpose that keeps same-trail analysis separately accounted, and a durable initial honey allocation. Work completion means the working tasks, the closing round, and the mandatory checks have passed, before final human approval and delivery; honey exhaustion alone is not completion.

Every cue invocation now mints a `cueinv-*` identity and records `.paseka/runs/<traceId>/cue-invocations/<invocationId>.json` before publishing `SIGNAL/cue.ingress` ahead of its normal task or signal events; the trail retains `origin.json` once, task specifications and projections carry `cueId`/`cueInvocationId`, and a later cue on an existing trail is recorded as an addition rather than a new origin. The seed transition writes a durable `energySeed` record and an `energy.seeded` observation for the winning allocation, which makes the initial budget readable without today's defaults. `paseka inspect metrics --trace <id> [--json] [--write]` projects retained disk evidence into the versioned (`schemaVersion: 1`) `TrailMetrics` object — cue origin and ingresses, class, fork lineage and configuration versions, work state/stage/revision/completion, honey, tokens, run and task dimensions, `byPurpose` work/closing/analysis splits, review and feedback counts, durations, and explicit coverage/warnings — and persists the same projection to `metrics.json`. Admission records execution purpose (`work`, `closing`, `analysis`) and `analysisOf`; an operator action is `paseka bee run|chat --purpose analysis --analysis-of <completionId>`, and configured analysis reactions subscribe to the milestone. The reactor publishes `SIGNAL/trail.work.completed` with `completionId`, `workRevision`, `completedAt`, `resultRef`, and `metricsRef` once every non-merge task and the mandatory checks have passed and working invocations, deferred dispatches, and an in-flight closing round have drained; before publishing it captures an immutable checkpoint, retained result evidence, the final patch when there is a code result, and a frozen metrics snapshot under `.paseka/runs/<traceId>/completions/<completionId>/`, so analysis can run in the original trail from retained evidence after delivery removes the worktree. Analysis does not hold completion, reopen the work revision, block merge or PR publication, or emit another milestone; explicitly admitted rework is ordinary work and can produce a later completion with its own identity.

What is not in this ship: the delivery outcome block and delivery record remain with [047](047-delivery-outcomes.md); statistics across many trails, cost in money, methodology choices, and promotion/quarantine are reader concerns listed under Out of Scope. Fork snapshot GC, a shared snapshot store, and experimental isolation stay with [042](042-trail-fork.md), and the closing-seed trigger keeps its ledger comparison (decision 3.12). The Console does not yet surface the retained origin or the metrics projection; `paseka inspect metrics`, `paseka trail show`, and the files under `.paseka/runs/<traceId>/` are the shipped read surface.

Related: [043a](043a-truthful-run-records.md) is the other half and must land first, because a metrics reader that counted a contract-downgraded run as `completed` would overstate success. [040-trail-event-log](040-trail-event-log.md) is the trail record these primitives read; [045-trail-closing-phase](045-trail-closing-phase.md) owns the `closing` and `merge` phases this spec projects; [046-bee-check-gate](046-bee-check-gate.md) supplies the gate verdicts it counts; [044b](044b-standing-supersession-and-energy-observations.md) supplies the pending/skipped admission vocabulary; [042-trail-fork](042-trail-fork.md) supplies the fork and configuration evidence; [047-delivery-outcomes](047-delivery-outcomes.md) owns delivery outcomes and the later `delivery` metrics block. Context: [idea: self-improving colonies](../idea/self-improving-colony.md).

## Problem Statement

A Beekeeper — or a role working for one — who wants to know whether the colony is getting better has to answer simple questions: how much did this trail cost, how many times was the same task rebuilt, did every run do what its contract said, and which trails were worth studying. Today every one of those answers needs a hand-written collector over `.paseka/runs/`.

**A trail does not know where it came from.** `paseka cue run` builds the task from the cue, and the task records the cue id — but nothing records the invocation, the ingress channel, or which cue started the trail. Two trails started by `feature` and by `hotfix` with the same Bee and intent cannot be told apart as trails afterwards, and a later cue on a running trail is indistinguishable from the one that created it. So "is this trail expensive for its kind" has no kind to compare against.

**There is no trail-level metrics surface.** `paseka inspect usage --trace` aggregates tokens, and `paseka export --include usage,durations` renders a human report. Neither gives the honey spent, the dispatches per task, the verification failures, the gate rejections, the closing overhead, or a contract outcome as one machine-readable object.

**There is no trail-level work-completion moment before delivery.** Per-task completion does not identify when the whole working result is ready for final approval. Requiring every task to be terminal is too late: the merge gate is still waiting before a merge, and PR delivery leaves it waiting even after a PR is published. Meanwhile [045](045-trail-closing-phase.md) added a closing round that runs after the work tasks and may plan more work — so "all work tasks completed" is now a moment *inside* the trail, not the end of it. A milestone fired there would announce a result the closing review has not yet judged.

**Nothing separates studying a result from producing it.** Analysis of a finished trail has no recorded purpose, so its cost and failures are indistinguishable from work, and a reader cannot tell an expensive trail from a well-studied one.

## Solution

Five primitives, exposed through existing run/event records and a new trail metrics read surface:

1. **Cue provenance.** Every cue invocation has a recorded ingress identity, including signal cues. The trail retains its original ingress separately from later additions, and task specifications retain the invocation that created them.
2. **Trail metrics.** `paseka inspect metrics --trace <id> [--json]` projects one trail into a versioned `TrailMetrics` object. The runtime records the initial honey allocation needed for offline reads, and persists metrics with each work-completion checkpoint.
3. **Work completed.** The reactor publishes `SIGNAL/trail.work.completed` once every non-merge task — work and closing — and the mandatory checks have passed, and their finalization has drained. It captures immutable work metrics before admitting analysis reactions. The merge gate, final human approval, and delivery do not gate this milestone.
4. **Execution purpose.** Admission records whether an execution serves the trail's work, its closing round, or analysis of the result. Metrics expose the three separately; root aggregates remain total observed activity.
5. **Durable initial allocation.** The winning seed's budget and seed time are recorded before the first charged dispatch, so an offline reader never infers a missing budget from today's defaults.

## User Stories

1. As a Beekeeper, I want a trail started by a cue to remember which cue and which invocation, so that I can compare trails of the same kind.
2. As a Beekeeper, I want signal cues and later cue invocations recorded separately from the original ingress, so that adding work does not rewrite where a trail came from.
3. As a Beekeeper, I want a later cue on a manually created trail to appear as an addition without inventing an origin, so that the trail's history stays honest.
4. As a Beekeeper, I want one command to print a trail's cost and rework counts as JSON, so that I do not maintain a jq collector.
5. As a Beekeeper, I want work metrics written when the trail's result becomes ready for final approval, so that a reader reads one snapshot instead of every run directory.
6. As a Beekeeper, I want metrics to report a missing measurement as missing, so that a trail without usage is not read as a free trail.
7. As a Beekeeper, I want a damaged or incomplete trail record to expose its measurement gaps, so that retained counts are not mistaken for exact totals.
8. As a Beekeeper, I want parallel runs and time spent waiting for human review to have explicit duration semantics, so that I can interpret the trail's timing.
9. As a Beekeeper, I want an interactive session's recorded usage included once, so that switching from AFK to HITL does not hide or double cost.
10. As a Beekeeper, I want a historical work-completion event to identify the result and metrics it announced, so that reopening the trail does not silently change that event's evidence.
11. As a Beekeeper, I want duplicate delivery and Reactor restarts to preserve a completion milestone's identity, so that a reader can handle the observation once.
12. As a Beekeeper, I want metrics to expose configuration changes and fork lineage, so that an aggregate from several procedures is not presented as one controlled experiment.
13. As a Beekeeper, I want analysis to stay in the original trail while its cost and failures remain separately visible, so that the work is not made to look worse or more expensive by studying it.
14. As a Beekeeper, I want analysis completion to leave the work-completion observation unchanged, so that a retrospective does not recursively trigger itself.
15. As a Beekeeper, I want execution and retry counts for custom task roles, so that renaming a Bee does not change the meaning of the metrics.
16. As a Beekeeper, I want analysis to continue from retained evidence if delivery removes the worktree, so that studying the result does not delay merge or PR publication.
17. As a Beekeeper, I want a paused or failed trail distinguished from completed work, so that exhausted honey is never presented as achieving the goal.
18. As a Beekeeper, I want a new trail's initial honey reserve recorded before work spends it, so that offline metrics preserve cue overrides and experimental budgets.
19. As a Beekeeper, I want the closing round counted as trail overhead rather than as goal work, so that a colony that reviews large change sets does not look like it works harder per task.
20. As a Beekeeper, I want a closing round in flight to hold the completion milestone, so that analysis does not start on a result the wrap-up may still change.
21. As a Beekeeper, I want the milestone to fire when no closing round is configured, so that a small trail is not made to wait for a phase its colony does not use.
22. As a Beekeeper, I want a waiting merge gate not to block the milestone, so that the result is readable before a human and a forge get to it.
23. As a Beekeeper, I want an unknown gate purpose to hold the milestone rather than be guessed, so that a mid-trail review stop is never mistaken for final acceptance.
24. As a Beekeeper, I want an old completion to be distinguishable from the trail's current work, so that a rework round does not rewrite history.
25. As a Beekeeper, I want a task superseded by a new standing allocation not counted as work, an execution, or a retry, so that a tick boundary is not reported as a defect.
26. As a Beekeeper, I want energy-deferred work to be visible as not-progress rather than as an idle trail, so that a pause is not read as completion.
27. As a Beekeeper, I want mechanical gate rejections counted per trail and per task, so that a flaky or mis-scoped check command is visible as a pattern.
28. As a Beekeeper, I want the trail's recorded stage in metrics to match the one the Console shows, so that two readers cannot disagree about where a trail sits.
29. As a Beekeeper, I want metrics and provenance to survive worktree-only cleanup, so that pruning a checkout does not erase what a trail cost.
30. As a Beekeeper, I want a trail's initial cue not to be inferred from its first task, so that a fork or a later addition cannot mislabel a trail's kind.
31. As a Beekeeper, I want honey-blocked, failed, cancelled, and skipped work to emit no success milestone, so that the observation always means what it says.
32. As a Beekeeper, I want substantive rework accepted after a completion to produce a new completion with its own identity, so that the newest result is announced and the older one stays historical.

## Implementation Decisions

### 1. Cue ingress and trail origin

1. Every validated cue invocation records an `invocationId`, `cueId`, ingress source/channel, emission mode, invocation time, and the identities of its normal ingress events and created tasks, if any. This applies to both `emit: task` and `emit: signal`, fresh traces, explicit existing traces, and standing ticks. Source cue identity is technical provenance, independent of Bee and intent names.
2. The cue subsystem writes a `SIGNAL/cue.ingress` observation through the canonical trail publisher before publishing that invocation's normal task/signal events. A repeated publication uses the same invocation/event identities; a genuinely new cue invocation receives a new identity. The observation records ingress intent, not a guarantee that every associated event reached the broker ([040](040-trail-event-log.md)). It does not itself create tasks, seed honey, or dispatch a Bee; normal ingress retains those responsibilities. It is excluded from AFK direct routing as a platform observation.
3. New trail creation/admission retains its initial ingress identity exactly once in a durable trail-owned origin record. All creation paths participate: a cue origin names its invocation, while manual or other origins do not invent a cue. Concurrent creation cannot select two origins. Adding a cue to an existing trail never replaces the origin. Source timestamps alone or the earliest task are insufficient to determine this identity.
4. Top-level metrics `cueId` names the initial cue only when the retained origin proves it; `cueIngresses` lists all distinct recorded cue invocations. A later cue on a manually created trail appears in that list but leaves the original cue field empty. Missing legacy origin remains unknown even when a later cue invocation is readable; do not label it initial merely because it is the first retained cue.
5. Task specifications, ledger snapshots, and task projections already carry an optional `cueId` for the cue that directly created the task; they gain `cueInvocationId` for the invocation that did. Role/manual task creation does not invent these fields. Signal ingress keeps its cue identity in the invocation record even though no task was created directly. Associated normal ingress events retain their invocation linkage without depending on a custom signal payload having a particular business schema.
6. **A task's `cueId` is not the trail's origin.** Fork lineage copies the source task's `cueId` into the fork, and any later task may carry a different cue. The origin record is the only evidence that can answer "which cue started this trail", and it is never derived from tasks.
7. Older events/tasks without provenance still decode. The durable origin and invocation records are retained with the trail and survive worktree-only cleanup. Cue definitions can change later; readers use recorded identities and available configuration evidence rather than today's cue contents.

### 2. Trail metrics

1. The run-record reader exposes a trail metrics projection from colony root and trace identity. It reads only retained disk evidence, so it works without NATS:
   - `trail-events.ndjson` ([040](040-trail-event-log.md));
   - run directories;
   - `tasks/*/task.md`;
   - proposal records ([039](039-proposal-patch-records.md));
   - the retained trail origin, seed observations, and work-completion evidence introduced here;
   - fork lineage and configuration snapshots where [042](042-trail-fork.md) evidence exists.
2. `TrailMetrics` uses `schemaVersion: 1`. The following is a field contract, not an assertion that all historical trails contain complete evidence:

   | Field | Meaning |
   | --- | --- |
   | `traceId`, `observedAt` | Trail identity and the projection's explicit observation time. |
   | `cueId`, `cueIngresses` | Optional initial cue identity, plus all distinct recorded cue invocations with origin/addition attribution. Coverage distinguishes known non-cue origin from unknown historical origin; neither invents a `manual` cue name. |
   | `class` | Entry-task descriptor (`taskId`, recorded `bee`, `intent`) plus total task count. It is `null` when no entry task can be identified. |
   | `work` | Recorded work state (`open`, `blocked`, `completed`, `failed`, `cancelled`, `skipped`, or `null` when unknown), the ledger stage (`work`, `closing`, `gate`, `delivered`), work revision, the current completion's identity/time/result reference when present, the active pending-dispatch count with its reasons, and the active energy-pause episode when one is open. Final acceptance and delivery are separate facts. An old completion may remain in history without describing the current work revision. |
   | `forkOf` | When [042](042-trail-fork.md) evidence exists, an object naming source trace, task, selected attempt/run, source configuration reference and revision. Values come from the retained fork record, not the source's current state. Otherwise `null`, with lineage coverage distinguishing known ordinary trails from unavailable provenance. |
   | `configuration` | Optional reference to retained configuration history, initial/active references, the distinct references actually used by recorded executions, and an explicit `multipleVersions` flag. Legacy unknown execution versions remain unknown. [042](042-trail-fork.md) supplies this evidence; its snapshot GC is deferred, so the flag describes retained evidence only. |
   | `honey` | Initial recorded `budget`, `spent`, and `byReason`. `spent` sums distinct recorded `energy.consume` amounts, not run directories. Newly seeded trails retain the effective budget; missing historical seed evidence yields `null`. Top-ups and stipends are recorded as additions, not as a replacement budget. |
   | `tokens` | Recorded input/output/cache-read/cache-write sums, `runsWithUsage`, and total `runs`; `null` when no run reports usage. Partial reporting is explicit. |
   | `runs` | Retained execution count, counts by Bee, `failed`, `cancelled`, `contractFailed`, `contractUnavailable`, `timeout`, `checksFailed`, and `checksPassed`. `checksPassed` counts gated runs whose gate recorded a pass; an un-gated run is neither. |
   | `tasks` | Stable task-id ordered task observations, with recorded `phase`, purpose/source completion, status, `executions`, `retries`, all joined run identities, verification failures, and gate rejections. Executions count the task's assigned work role, independent of its name. |
   | `byPurpose` | Separate `work`, `closing`, and `analysis` measurements for honey, tokens, runs, failures, retries, verification/review observations, gate rejections, and execution time. Root aggregates remain total observed trail activity. |
   | `verificationFailed` | Count of distinct recorded `VERIFICATION/verification.failed` events, including events not joined to a task. Gate rejections are included here as well as in their own counters. |
   | `reviewNotes` | Counts by `info`, `low`, `medium`, `high`, `critical`, `unspecified`, and historical `unknown`. |
   | `humanFeedback` | Counts by `negative`, `positive`, `neutral`, `unspecified`, and historical `unknown`; these are feedback events, not all human review decisions. |
   | `activeTimeSec` | Sum of recorded execution intervals; overlapping runs add, so this may exceed wall time. |
   | `wallTimeSec` | For a live total projection, elapsed time from the earliest retained ingress/task/execution evidence to `observedAt`. For a work-completion snapshot, elapsed time to `completedAt`; includes working review waits, closing rounds, and honey pauses, but excludes later final approval, delivery, and analysis. |
   | `coverage`, `warnings` | Completeness (`complete`, `partial`, `unavailable`) by measurement group and concrete reasons for missing, unreadable, conflicting, or legacy evidence. A non-null partial total describes retained observations only. |

   **Projection rules:**

   - Use the common trail-scoped merged event reader and deduplicate by event identity before counting. The log records publication intent before the broker attempt ([040](040-trail-event-log.md)); an event count is not proof of broker delivery or successful ledger application. Accepted task state comes from the runtime's task projection/lifecycle evidence, not blindly replaying every recorded publication.
   - The entry-task descriptor is selected deterministically from known non-merge tasks by earliest `createdAt`, then `taskId`. It is a descriptor, not proof of a unique causal root; multi-task intake can have several roots. Unknown creation time makes classification partial. Do not consult current colony defaults to fill historical Bee or intent values.
   - `work.stage` uses the same ledger predicates as the trail detail's derived stage, so the Console and the metrics file cannot disagree about whether a trail is working, closing, at the gate, or delivered.
   - Count each retained execution once. AFK usage comes from the run result; interactive usage may come from the session record. If both represent the same execution, choose one source rather than summing both. Missing usage differs from reported zeros, and an explicitly unavailable usage source is not a measurement.
   - `request.json` supplies task-to-run joins for both task and direct dispatch; task `runs.ndjson` alone misses direct-dispatch runs. An unjoinable execution remains in trail totals with a warning. Reuse of an execution directory may have overwritten earlier results: retained execution counts cannot claim to count every historical dispatch. Honey charges and execution counts need not match.
   - `runs.failed` counts primary failed status; timeout is normally a cancelled run with reason `timeout`. `contractFailed` and `contractUnavailable` count explicit verdicts, including for an already-failed adapter run. `checksFailed` counts runs whose mechanical gate rejected them and is normally also a failed run. These dimensions may overlap and must not be added together as a total failure count. Missing legacy contract evidence affects coverage, not the explicit-verdict counters; it proves neither a successful contract nor an evaluation failure.
   - Per-task `executions` counts invocations performing the task's assigned work role, using execution-time ownership rather than a literal role name or today's registry. Guard and other associated roles remain in total joined runs but do not become task retries merely because they share a `taskId`. Direct-dispatch rework and HITL execution count when they perform the assigned work role. `retries = max(0, executions - 1)` includes repeats after crashes, operator retries, gate rejections, and returns after verification; it does not claim to count code rework alone. Missing historical ownership makes this measurement partial/unavailable rather than authorizing a guess. [042](042-trail-fork.md)'s task-attempt identity is distinct from an invocation count.
   - A task with status `skipped` — deliberately not delivered because a new standing allocation superseded it ([044b](044b-standing-supersession-and-energy-observations.md)) — contributes no execution, no retry, and no completion. A task with an active energy-deferred pending entry has not started, whatever its lifecycle status says.
   - Per-task verification failures join on recorded `taskId`. Their sum may be smaller than the trail total because taskless verifications remain visible. Verification failures are independent observations; they are not converted into retries. `checksFailed` on a run and a `verification.failed` with reason `checks_failed` usually describe the same rejection from two recorders and must not be added as two events.
   - Work-completion comparisons use `byPurpose.work` from the frozen snapshot, not its root total aggregates. This baseline includes cumulative work on the goal through that revision, including earlier failed work executions, but excludes closing rounds and analysis of every revision. Closing is trail overhead: it exists only for colonies that enable the policy, so folding it into the work baseline would make a wrapped-up trail look more expensive than a small one for the same goal. Live total aggregates may continue growing as closing and analysis run in the same trail.
   - Analysis stays in the total Honey Reserve and all trail records; it is not a free dispatch and cannot bypass honey exhaustion or kill. Work revision identifies accepted goal work and is distinct from [042](042-trail-fork.md)'s configuration revision.
   - Initial honey reserve is currently seeded directly in the ledger. V1 adds a durable `SIGNAL/energy.seeded` observation with the winning seed identity, effective budget, and actual seed time. The authoritative seed transition retains this observation's identity/data so a crash between ledger commit and local publication can be repaired without reseeding or choosing a new event identity. It is captured before the first charged dispatch, through every seed path: colony defaults, cue override, standing first seed, session entry, and experimental budget.
   - `energy.seeded` observes an already accepted allocation; receiving/replaying it must not seed/add/consume again or dispatch a Bee. A competing seed request observes the existing winner rather than logging its own proposed budget. Pending observation publication retries use that winner. Legacy ledger entries lacking seed provenance are not assigned an invented historical timestamp or configuration. Offline readers never infer a missing budget from current colony/cue defaults.
   - Top-ups and standing stipends retain their existing semantics and do not replace the original seed observation or its `budget`. A budget is not total lifetime expenditure. Per-purpose spending divides charges, not the shared budget allocation; work, closing, and analysis use one recorded reserve.
   - Durations use recorded timestamps with non-negative intervals and a single explicit `observedAt`. Running executions use `observedAt` as their temporary end. Missing or invalid timestamps make the corresponding duration partial or unavailable; no usable intervals yields `null`, not zero. Observation/completion events and metrics-file modification times are excluded from the start/end calculation.
   - Empty, missing, or malformed sources do not silently become exact zero counts. A missing trail is a CLI error. A readable partial trail returns observed values with coverage/warnings. Live reads are observations that may race updates; only the runtime's work-completion barrier can certify a completion snapshot.
3. CLI: `paseka inspect metrics --trace <id> [--json] [--write] [-C dir]`. This follows `inspect usage`'s flag style. Without `--json` it prints a short table and measurement warnings. The default read does not write files or publish events; `--write` persists the same projection that the invocation prints and does not itself declare work completed.
4. **Persistence.** `.paseka/runs/<traceId>/metrics.json`, written atomically:
   - by the reactor before announcing `trail.work.completed` (primitive 3), alongside an immutable snapshot for that completion;
   - by `inspect metrics --write`.

   A completion's `metricsRef` is a colony-root-relative reference to its immutable trail-owned snapshot; `metrics.json` is a replaceable convenience projection and is not the target of historical completion references. Readers exclude these record directories from execution counts. Retention targeting run data removes the projections and snapshots with the trail; worktree-only pruning leaves them readable. A long-term history beyond retained trail data belongs to the reader (e.g. a methodology's own store).
5. The `delivery` block is owned by [047](047-delivery-outcomes.md) and added additively when it lands; it does not bump `schemaVersion`.

### 3. `trail.work.completed`: before final approval and delivery

1. A new `SIGNAL` kind `trail.work.completed` carries `completionId`, `workRevision`, `completedAt`, `resultRef`, and `metricsRef`; the envelope identifies the trail. It announces that the accepted working set and its mandatory checks have passed. It is not a general idle notification and not proof of human acceptance. This replaces the draft-only `trail.settled` design; no compatibility alias is required for an unshipped event.
2. The predicate is "every non-merge task is completed": ordinary work and every closing round. It requires at least one working task — a taskless or event-only trail is not complete by vacuous truth; automatic completion for such a goal needs a separate contract. A merge task at `waiting_review` does not block the milestone. Unknown gate purpose is not silently excluded: if the review evidence cannot say whether a waiting review is final acceptance or a work gate, the milestone holds.
3. **The closing round is a mandatory check, not final acceptance.** [045](045-trail-closing-phase.md) seeds a closing round after the work tasks complete; it may plan further work. A milestone fired on "all work tasks completed" would announce a result the wrap-up has not judged, and analysis would start on a candidate that may still change. `AllWorkCompleted` therefore remains the internal trigger that seeds the closing round and emits nothing. When the pinned policy seeds no round — disabled, predicates unmatched, cap reached — there is nothing left before the gate and the milestone may fire as soon as work completes.
4. Ordinary task-level `review: required` remains a work gate when further substantive work depends on it. Review records explicitly distinguish work-enabling review from final goal acceptance; `waiting_review` alone is insufficient to make that distinction.
5. A code result with no isolated proposal also qualifies when its work and checks are done. The runtime's existing empty-gate activation rules decide whether there is anything to merge; the milestone does not depend on that decision.
6. The runtime evaluates after working task transitions, mandatory verification, closing-round transitions, work direct-dispatch completion, registered work-session completion, and run finalization. A hook in `applyAndSync` alone misses paths and runs before the last dispatcher leaves its in-flight set. The barrier serializes with new work admission and requires working invocations, pending work dispatches ([044b](044b-standing-supersession-and-energy-observations.md)), required work finalization effects, and an in-flight closing round to have drained. Persisted results, task projections, usage, and result evidence must be ready. Final approval, PR review, analysis runs, and delivery reconciliation are not outstanding work for this predicate.
7. Snapshot and result references resolve to immutable trail-owned evidence for that completion. For a code result, retain the relevant base/revision and final patch or equivalent retained tree evidence before delivery can remove the execution worktree; retain the non-code result artifacts needed to inspect other outcomes. Analysis must not depend on a mutable live worktree or mutable handoff file as its only input. Required evidence failing to persist is a visible finalization error, not a successfully announced completion.
8. The checkpoint, completion identity, and snapshot are durable before event publication and before delivery is allowed to remove their source evidence. Completion publication failure is retryable with the same identity; it does not require analysis to run before delivery. A fast final-approval action must ensure that the corresponding checkpoint is captured before its delivery side effects. Delivery and analysis then proceed independently under existing permissions.
9. Work that is blocked, failed, cancelled, skipped, energy-deferred, or waiting on an unfinished dependency does not emit this signal. Metrics remain inspectable for those states. `energy add` only makes blocked work runnable; it does not assert goal completion. No general paused/failed/cancelled notification protocol is introduced here.
10. Durable `completionId` survives Reactor restart, duplicate events, and publish retry. Bus delivery is at least once; consumers deduplicate by completion identity. New accepted substantive work, including requested changes at the gate, reopens work and advances its revision. A later completion receives a new identity. Final approval, PR publication or merge, repeated reads, analysis activity, and late narrative notes do not themselves create a new work revision. An older completion remains historical when new work is accepted.
11. `workRevision` identifies the accepted goal work a completion describes. It advances when substantive work is accepted into the trail — a new work-phase task, a rework return, or rework planned from a gate rejection — and not when a closing round is seeded, when analysis runs, or when the milestone fires. It is what lets an old completion be told apart from the trail's current work.
12. **The milestone is not the closing-seed trigger.** [045](045-trail-closing-phase.md) Further Notes anticipated replacing its "new work completed after the last closing round" comparison with this revision; that is not possible without making the milestone fire before the round it is meant to wait for. The closing seed keeps its ledger comparison, and any future closing trigger uses accepted-work facts, never this observation.
13. Read-only inspection never emits the milestone; `--write` does not certify completion. The runtime records completion for accepted work at that boundary and cannot promise that a delayed external request will never arrive. This event alone does not establish semantic success beyond the task and check contracts recorded for that goal.
14. Work completion, final acceptance, analysis, and delivery are separate observations. Existing `local_merge`, PR publication, reconcile, root soft acceptance, and experimental no-delivery behaviour are unchanged. The delivery outcome vocabulary and its record belong to [047](047-delivery-outcomes.md) and are not overloaded onto this milestone.

### 4. Analysis in the original trail

1. Execution admission records purpose `work`, `closing`, or `analysis`. For task dispatch the purpose follows the recorded task phase; an explicitly configured analysis reaction or operator-started analysis action records `analysis` and the work milestone it studies (`analysisOf`); the source trace remains unchanged. Purpose is runtime-owned provenance, not inferred from the Bee's name or free-form output. Ordinary work defaults to `work`; unsupported historical attribution stays unknown and cannot be silently excluded as analysis.
2. Analysis-owned tasks, direct dispatches, sessions, and emitted events retain their purpose and source milestone through their causal chain. Metrics expose work, closing, analysis, and total activity separately. A failing analysis run is visible as an analysis failure; it does not retrospectively turn successful work into failed work.
3. Analysis activity and its narrative events do not reopen the work episode, satisfy or block work-task completion, or generate another work-completion milestone. Final-gate activation and change-request eligibility must evaluate the working task set rather than treating analysis tasks as unfinished product work. Reader dispatch is deduplicated by source milestone and analysis subscription/action identity, including after restart. Explicitly retrying failed analysis remains possible and is counted within analysis.
4. Findings can recommend additional work, but accepting substantive rework is an explicit normal-work admission. That reopens the work episode, creates new work evidence, and can later produce a new completion milestone. Analysis attribution must not silently exempt implementation changes from work accounting. Analysis inspects the captured result and does not mutate the candidate being reviewed; changing that result is ordinary work subject to its checks.
5. Analysis can run alongside final review and does not block merge or PR publication. Its launch workspace must be independent of the removable delivery worktree, while its run/audit records remain in the same trace. It reads the captured evidence even if delivery already removed the original worktree. Existing configuration provenance, Honey Reserve, and kill controls still apply. Analysis has no implicit merge, push, or publication permission; adding a separate mandatory-analysis policy is out of scope for v1.

## Testing Decisions

Tests assert observable persisted outcomes, published events, and CLI output, using fake adapters and local fixtures rather than model calls. Work completion before final approval, non-blocking same-trail analysis, role-independent retries, durable initial allocation, and complete cue-ingress provenance are selected.

- **Provenance:** task cues retain cue and invocation identity in the ledger and task projection; signal cues retain it without needing a task. Repeated normal events for one invocation do not duplicate ingress counts. Later cues on an existing manual trail leave origin unchanged; concurrent creation converges on one origin. Multi-task plans with equal timestamps do not choose origin by task ordering. Legacy unknown origins and old events remain readable without invented provenance. A fork whose tasks carry the source cue id does not report that as its own origin.
- **Metrics:** fixtures cover rework, adapter retry, a custom task role, a closing round, honey block and top-up, parallel runs, human review waits, interactive usage, absent usage, reported zero usage, missing seed evidence, taskless verification, a gate rejection, a `skipped` task, and overwritten run evidence. Counts deduplicate an event recorded twice or present in both event stores. Timeout, contract, and check dimensions do not incorrectly inflate primary failed totals. Closing and analysis measurements appear in `byPurpose` and not in `byPurpose.work`.
- **Read/write contract:** for one invocation and observation time, printed JSON and `--write` output agree. Default reads change no files or bus state. Missing trail is an error; partial/corrupt records expose coverage and warnings. Worktree-only cleanup leaves metrics and retained provenance readable.
- **Work completion:** the last working task completes while its dispatcher is still in flight → no premature event; leaving the in-flight set triggers the check. A waiting merge gate permits the event. An unfinished required work review does not. A closing round in flight blocks it; the milestone fires when that round completes; with the policy disabled or the cap reached it fires at work completion. A root R1 final acceptance uses explicit work and check evidence without an invalid isolated final-review policy. Unknown gate purpose is not guessed. No-code/no-delivery work also completes. Honey exhaustion, an active energy-deferred pending entry, task failure, cancellation, a `skipped` task, standing ticks, and empty ledgers do not emit a success milestone. New accepted work reopens the revision; publication retry and restart retain the completion identity. Old events still resolve to their original result and metrics. Final approval, PR publication, PR merge, and narrative events do not produce another work completion.
- **Approval race and retained evidence:** immediate approval and delivery after work completion cannot remove evidence before checkpoint capture. Failed capture is visible. After a successful checkpoint, merge or PR publication can proceed without waiting for analysis, even if milestone publication needs retry. Analysis can start or finish from retained evidence after the source worktree is removed.
- **Configuration and lineage:** with [042](042-trail-fork.md) records, metrics retain the selected source attempt and configuration history; multiple versions are visible. Without those records, they do not substitute today's configuration or prevent basic metrics reads.
- **Analysis scope:** analysis in the source trace increases total and analysis usage but leaves the frozen work snapshot unchanged. Analysis failure, completion, retries, and emitted notes do not reopen work, recursively dispatch the same analysis, or block final approval and delivery. Analysis-owned tasks do not suppress final-gate activation or legitimate change requests. Restart preserves attribution and duplicate suppression. Explicitly admitted substantive rework is counted as work and can produce a new work milestone.
- **Role-independent retries:** a custom task role behaves like any other assigned work role; one task execution plus one Guard execution yields zero task retries, while a second execution of the assigned work role yields one. Verification failure without another execution does not invent a retry. A gate rejection followed by a builder rework yields one retry and one recorded gate rejection, not two. Historical unknown ownership is reported as a coverage gap.
- **Seed evidence:** default, cue, standing, session, and fork allocations record the actual winning initial budget. Concurrent seed requests, interrupted publication, and restart neither duplicate allocation nor choose a second seed identity. Observation replay does not alter honey. Top-up and stipend leave the initial budget unchanged; old trails without evidence return an unknown budget rather than current defaults.

Prior art: runtime completion and dispatch tests, run/task projection and usage tests, trail-event identity and merge tests, task-ledger energy tests, closing-round and merge-gate tests, check-gate result tests, review-gate tests, session accounting tests, and prune retention tests.

## Out of Scope

This spec is the **recorder**. Everything that turns records into decisions belongs to a reader, and a reader is either a person or content shipped as a methodology.

- **Statistics over many trails** — norms, percentiles, class medians, "this trail is expensive for its kind". A reader computes those from the metrics; the runtime does not maintain a baseline.
- **Deciding that a trail is worth studying.** Which trails are interesting, and what counts as a defect, is a judgement. The runtime publishes `trail.work.completed` and the metrics; a reader decides. Analysis of paused or failed work can be requested explicitly; this success milestone is not their trigger.
- **Noise discipline.** How many runs count as evidence for a claim is a methodological choice, not a platform guarantee.
- **Promotion, quarantine, rollback.** Deciding that a procedure helped and disabling one that hurt is content, not a runtime primitive.
- **Benchmark suites, `pass@k`, scoring.** That is the eval colony's business ([spec 003](003-hive-evals.md)).
- **Cost in money.** Token counts are recorded; a price table is the reader's.
- **Delivery outcomes and the delivery record** — [047](047-delivery-outcomes.md) owns them, including the later additive `delivery` metrics block.
- **A colony-wide metrics database.** Metrics and immutable work-completion snapshots are trail-local projections of retained evidence. Missing historical measurements are reported explicitly; specs 039 and 040 alone do not supply every proposed field (notably the initial honey reserve).
- **Changing delivery semantics.** This milestone precedes final approval and does not close a PR-backed gate, merge, push, or grant delivery to an experiment.
- **Re-executing history from JetStream.** `paseka replay` stays inspect-only.
- **Experimental execution isolation.** [Spec 042](042-trail-fork.md) owns trail configuration bindings, pinned fork policy, workspaces, and consumer scope on the colony's shared Reactor and bus. This spec only exposes their recorded provenance.
- **Rewriting the closing-seed trigger.** [045](045-trail-closing-phase.md) keeps its ledger comparison; see decision 3.12.

## Further Notes

### Resolved decisions

- **D1 — Work completion precedes final human approval and follows the closing round.** The accepted working set is every non-merge task: ordinary work and the closing review. A waiting merge gate, final approval, and delivery are still ahead. Honey-deferred, failed, cancelled, and skipped work are not this success milestone. Use `trail.work.completed` rather than a generic idle/settled notification.
- **D2 — Analysis stays in the source trail and does not gate delivery.** Work-completion evidence is frozen before analysis; execution-purpose provenance keeps analysis visible in total cost while excluding it from the work baseline and completion trigger. It may run alongside final review and continue from retained evidence after delivery removes the worktree.
- **D3 — Execution and retry counts are independent of role names.** Count the task's recorded assigned work executions and `max(0, executions - 1)` retries, with verification failures and gate rejections separate. Do not publish a return-for-rework metric without causal evidence.
- **D4 — Persist initial honey allocation in v1.** Record the authoritative seed winner and recover interrupted observation publication without allocating twice. Historical absence remains unknown; new defaults never fill old metrics.
- **D5 — Cover every cue ingress.** Record task and signal invocations, retain the trail's original ingress separately, and distinguish later additions without rewriting origin.
- **D6 — Delivery outcomes.** Moved to [047-delivery-outcomes](047-delivery-outcomes.md), which opens the delivery record this spec deliberately does not define.
- **D7 — Closing is overhead, not goal work.** `byPurpose` separates it from `work` and `analysis`, and the completion milestone waits for it. Counting it as work would make the same goal cost more on trails whose colony enabled the policy.

### Delivery and interpretation

- **Order of landing.**
  1. [043a](043a-truthful-run-records.md) first: the truthful records and closed vocabularies this projection depends on.
  2. Origin/ingress records, seed evidence, purpose attribution, retained result evidence, and work-completion checkpoints before the corresponding read surfaces and milestone publication. [047](047-delivery-outcomes.md) owns the later delivery protocol; this spec does not wait for it to define work completion.
  3. [Spec 042](042-trail-fork.md) already writes the configuration and lineage evidence the `forkOf` and `configuration` fields read; the fork's `forkOf` slot is why `TrailMetrics` has that field.
- **Why not a metrics daemon.** Metrics are derived from retained records. Additional evidence needed for a promised field must be recorded by its existing owning subsystem or reported as unavailable; a background service cannot reconstruct missing history.
- **Measurement, not proof.** `TrailMetrics` says what a trail cost, not whether the cost was avoidable. The same rule as [spec 041](041-skills-layer.md)'s attribution note: a recorded use means a file was read, not that its instructions were followed.
- **The boundary this spec protects.** A colony that can read its own records can have a reader for them — a person, a script, or a methodology pack. A colony that cannot read its records can only have a reader that parses logs, which is how a runtime ends up carrying an LLM's bookkeeping in its prompts. This spec keeps the bookkeeping in Go, where it is deterministic, and leaves the judgement to the reader.
